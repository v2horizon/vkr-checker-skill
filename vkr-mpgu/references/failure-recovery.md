# Сценарии провала и план восстановления

Реальные ВКР редко идут по идеальной траектории. Этот файл — playbook для частых кризисных сценариев. Читай в момент проблемы, не заранее.

## Сценарий 1: Оригинальность ниже нужного уровня

### Симптом

Работа рискует не набрать уровень оригинальности, который требует кафедра. Шкала
базовой методички (ориентир оценки, не гарантия): обычная ВКР — 80%+ «отлично»,
70–79% «хорошо», 50–69% «удовлетворительно», ниже 50% работа может быть оценена
«неудовлетворительно»; проектная — 90%+, 80–89%, 70–79%, ниже 70% — риск
«неудовлетворительно». Рабочая цель скилла выше этих границ (`SKILL.md` →
«Практические пределы humanizer») — не требование.

**Важно:** официальная проверка в Антиплагиат.Вуз проходит **один раз**
(методичка). Поэтому доработка по стратегии ниже возможна только **до** официальной
проверки — по признакам риска, собственной предварительной проверке фрагментов
или по отчёту, если кафедра сама предусматривает предварительную проверку. После
официальной однократной проверки текст ради процента не переписывают — см.
«Если результат официальной проверки уже получен».

### Немедленные действия (первые 24 часа)

**1. Детальный анализ.** Если есть отчёт с разметкой совпадений (цветами) — смотреть, **какие фрагменты** и **с чем** совпали. Если отчёта нет — прочитать теоретическую главу и введение на предмет пересказа учебников и длинных цитат.

**2. Категоризация совпадений:**
- **Цитаты в кавычках с корректной ссылкой** — это не должно засчитываться. Если засчитано — это вопрос оформления ссылки, его обсуждают с научным руководителем
- **Клише научной речи** — «на современном этапе», «представляется обоснованным» — засчитываются мелкими процентами, но вычитаются только переписыванием
- **Технические термины и нормативные формулировки** — их оставляют как есть; искажать термины и цитаты ради процента нельзя
- **Массовые совпадения** (большие блоки текста) — главная проблема; требуют переписывания

### Стратегия доработки по приоритету (до официальной проверки)

**Небольшой риск (отдельные совпадающие абзацы):**
Переписать самые «красные» блоки. Обычно это 3-5 параграфов из теоретической главы (там чаще всего компилятивный пересказ). Применить технику глубокого парафраза из `originality-techniques.md` (смена структуры предложения, не синонимов).

**Системный риск (компиляция по всей главе):**
Вероятно, теоретическая глава имеет высокую долю непереработанных чужих идей. Решения:
- Заменить 5-10 значимых абзацев на **собственный синтез 2-3 источников**
- Добавить авторские безличные обороты и комментарии (индивидуальные якорьки из state-файла — см. `humanizer-techniques.md`; **не копировать** фразы-примеры из других файлов скилла)
- Убрать длинные цитаты, оставить только короткие ключевые со ссылкой

**Работа в основном собрана из чужих текстов:**
Работа требует серьёзной переделки, не косметики. Обсудить с научруком **перенос защиты**. Если сдвиг невозможен — написать в кратчайший срок 2-3 новых параграфа, максимально связанных с реальным продуктом и пилотом.

Все правки вносятся в `drafts/*.md`, затем пересборка и проверка по `quickstart.md`, шаг 4.

### Чего НЕ делать

- **Не применять** символы-обходилки (замена «о» на латинское «o» и т.п.) — Антиплагиат.Вуз помечает это отдельно как попытку обхода, и это **дисциплинарное нарушение**.
- **Не использовать онлайн-синонимайзеры** — дают неестественный текст, ловится детектором ИИ и нормоконтролем.
- **Не паниковать и не переписывать всё за ночь** — получится хуже оригинала.

### Если результат официальной проверки уже получен

В базовой методичке МПГУ предусмотрена **одна проверка**; второй попытки обычно
нет. Результат 50–69% для обычной ВКР и 70–79% для проекта по шкале методички
соответствует уровню «удовлетворительно», но проценты сами по себе не гарантируют
допуск или оценку: решение зависит от содержания и правил программы. Сверь отчёт с
научным руководителем и кафедрой; вопросы к разметке (например, засчитанные
оформленные цитаты) обсуждаются через них. Скилл не обещает повторной проверки.

## Сценарий 2: Детектор ИИ показал HIGH или CRITICAL

### Симптом
Прогонка через `ai_detection_heuristic.py` или (что хуже) через реальный детектор показала высокий риск на каких-то разделах.

### Диагностика по флагам

**«LOW burstiness» (низкая рваность):**
Абзацы слишком одинаковые по длине. Лечение:
- Найти 5-10 абзацев одинаковой длины подряд
- Один укоротить до 1-2 предложений («коммент»), один удлинить до 7-8 («развёрнутый разбор»), один разбить на два
- Добавить одно короткое острое предложение после длинного

**«Too many AI strong cliches»:**
Переобилие «стоит отметить», «важно подчеркнуть», «в свою очередь», «таким образом».
- Прогнать Ctrl+F по каждой фразе, **заменить на конкретный переход** («Данный подход прослеживается и у…», «Однако…», «В частности, …»)
- Норма: не больше 1-2 таких оборотов на всю работу

**«Poor lexical diversity»:**
Словарь беден, много повторов ключевых слов.
- Найти 5-7 самых частых существительных/прилагательных
- Половину заменить на синонимы
- Часть — через переформулировку («важный» → «определяющий», «структурообразующий», «центральный»)

**«Monotonous paragraph rhythm»:**
Подряд 5+ абзацев одной длины. Разбить/объединить, чтобы максимум 3 подряд похожих.

**«No author voice»:**
Текст механический. Добавить в 3-5 местах **индивидуальные** безличные авторские якорьки из state-файла пользователя (не копировать из примеров — иначе кросс-матчинг).

### Приоритет переработки

1. **Сначала — введение и заключение** (они оцениваются внимательнее)
2. **Потом — Глава III / проектная часть** (там конкретика, проще вставить детали)
3. **В конце — теоретическая глава** (если времени нет — можно оставить без переработки; маркеры в тексте на финале недопустимы)

### Если HIGH остаётся после переработки

- Применить Test-30 из `defense-mastery.md` — проблемные фрагменты **переписать целиком своими словами**, не правя по фразам
- Это самый надёжный способ; занимает больше времени, но решает проблему на содержательном уровне

## Сценарий 3: Научрук отверг главу целиком

### Симптом
«Перепишите Главу II, подход неверный» / «Это не то, что мы обсуждали» / «Слишком поверхностно».

### Разбор ситуации

**Не паникуй. Обычно это означает:**
- **Неверно понято задание** научрука — обсудить детально, что именно нужно
- **Не учтены специфические требования кафедры** — узнать, есть ли примеры, как должно быть
- **Претензия к глубине** — научрук хочет больше разбора, больше источников

**Не означает:**
- Вся работа плохая (если плоха одна глава, остальные могут быть в порядке)
- Надо начинать с нуля (почти никогда)

### Тактика работы с отказом

**Шаг 1. Личная встреча (не письмо).** Обсудить 30-40 минут:
- Что конкретно не так?
- Какие параграфы/тезисы особенно проблемны?
- Есть ли похожая работа-образец у научрука?

**Шаг 2. Переработка по конкретным критериям.** Никаких «переработать всё».
- Выписать 5-8 конкретных пунктов критики
- Для каждого — решение (переписать, добавить, удалить, перенести)

**Шаг 3. Частичная переработка в подаче `draft`.** Не `final`. Быстро сделать новую версию проблемной главы, показать научруку **промежуточный результат** (не финал) за 3-4 дня.

**Шаг 4. Итерация до зелёного света.** Обычно 2 итерации достаточно.

### Через скилл

Когда пользователь пишет «научрук отверг Главу II», ИИ-агент должен:
1. Запросить **конкретный список претензий**, не общие слова
2. Запросить **сами правки** от научрука (если в письменном виде)
3. По каждому пункту предложить **конкретное изменение**
4. Переписать проблемные параграфы в подаче `draft` (быстро, ещё не полировка)

## Сценарий 4: Пилот провалился или не состоялся

### Симптом
Планировался пилот с 15 школьниками в апреле, но дирекция отказала / участников меньше 5 / результаты противоположны ожиданиям.

### Адаптация работы

**Участников меньше запланированного:**
- Порог 5 участников из базовой методички относится только к частной образовательной практике. Для другой базы обосновать фактический размер выборки и согласовать его с научным руководителем.
- Если пилот не состоялся совсем, не придумывать результаты. С научным руководителем выбрать реальную альтернативу проверки или, как крайнюю меру, изменить формат ВКР.

**Пилот прошёл, но результаты противоположны гипотезе:**
- **Это нормально** и научно ценно. Переформулировать в заключении: «Гипотеза не подтверждена, выявлены следующие ограничения…»
- Добавить в Главу III анализ **почему** гипотеза не сработала (это часто интереснее, чем подтверждение)
- Комиссия ценит честность больше, чем подгонку под ожидаемый результат

**Справка о внедрении не получена:**
- Сначала проверить документы программы: приложенная базовая методичка содержит
  форму справки, но её обязательность нельзя переносить на все направления
- Если справка входит в обязательный комплект, немедленно согласовать с
  научным руководителем допустимый способ документировать реально проведённую
  апробацию или изменение формата работы
- Нельзя подменять место апробации, подпись, выборку или результаты ради справки

## Сценарий 5: Дедлайн внезапно сдвинулся на раньше

### Симптом
Защита перенесена с июня на май. Осталось 3-4 недели вместо 6-8.

### Немедленная приоритизация

**Что можно ускорить:**
- Переход на подачу **`draft`** для всего нового текста
- Отказ от humanizer-переработок для **теоретической главы** (там нет защитных рисков, текст может звучать шаблоннее)
- Сокращение числа используемых источников до реально проверяемого объёма. Непроверенные источники не включать в утверждения и не оставлять их проверку на последние сутки.

**Что нельзя ускорить:**
- Mastery-протокол для практической главы (без этого защита провалится)
- Финальная полировка введения и заключения (они критичны для первого впечатления комиссии)
- Проверка оформления через валидатор

**Что можно срезать:**
- Количество источников — до подтверждённого минимума программы; если порог не
  указан, согласовать реалистичный объём с научным руководителем
- Глубину теоретического обзора (компактнее)
- Количество приложений (только критичные)

### Режим «выживание»

Если осталось меньше 2 недель:
- Работа пишется в подаче `draft`
- Humanizer применяется только к **введению и заключению** (это 20% работы, но 80% внимания комиссии)
- Mastery применяется только к 3-4 ключевым параграфам на защиту
- Формальный валидатор — обязательно, без него может не пройти нормоконтроль

Такая версия вряд ли получит «отлично»; допуск и оценку определяют кафедра и комиссия, скилл их не гарантирует. Работа на «хорошо» или «удовлетворительно» — **приемлемый исход** в ситуации сдвига дедлайна. Сократить срок можно и сменой режима: `mode` в `vkr-project.json` по таблице сроков в `SKILL.md`.

## Сценарий 6: Случайно удалил/потерял файлы

### Симптом
«Утром удалил что-то не то, вся работа пропала».

### Восстановление

**Если проект создан скиллом** (есть `vkr-project.json`):
- Запустить `python <SKILL_DIR>/scripts/vkr_memory.py <PROJECT_DIR> status --json`: он покажет изменённые и исчезнувшие файлы (`missing`) по индексу `memory/artifact-index.json`; `recovery_required` — повреждена или прервана запись памяти.
- Прежние версии DOCX и черновиков лежат в `backups/checkpoints/`: копии перед каждой сборкой (`<UTC>-build/`), обновлением полей (`<UTC>-fields/`), импортом (`<UTC>-import/`) и крупными правками.
- Если сохранился `final/vkr.docx`, а черновики потеряны — вернуть текст в проект: `python <SKILL_DIR>/scripts/import_docx.py <PROJECT_DIR> --docx <PROJECT_DIR>/final/vkr.docx --update`. Отсутствующие черновики создаются заново, ссылки `[N]` возвращаются в `[@id]` по `exports/citation-map.json`, `sources.json` не меняется. Если потерян `exports/citation-map.json` — только `--force`: черновики получат числовые ссылки `[N]` по списку литературы DOCX. Реестр со структурированными или проверенными записями при этом сохраняется, а список литературы DOCX пишется в `audit/sources-extracted.json` — сверь номера с `id` реестра (`source-verification.md` → «Перенос извлечённых записей в реестр»). Если потерян и сам реестр, `--force` создаст его из записей `raw_text`; заменить уцелевший реестр можно только `--force --replace-sources` (прежние файлы — в `backups/checkpoints/<UTC>-import/`).
- Если повреждены `audit/manifest.json`, снимки или отчёты — причина остановки `RECOVERY_DATA_REQUIRED`: не начинать новые run поверх потерянного состояния, восстановить файлы из резервной копии; прежние волны на новом снимке не засчитываются.

**Если state-файл был:**
- Там зафиксирована структура и ключевые решения — можно быстро восстановить каркас
- Тексты глав придётся восстанавливать из резервных копий или из последнего DOCX

**Если проект в Git-репозитории (Gitea / GitHub):**
- `git reflog` → восстановление в течение 90 дней по умолчанию
- Даже если `rm -rf` — если был хотя бы один коммит, файлы в object store Git живы

**Если работа велась только в чате без файлов:** история переписки — ненадёжная память. Скопировать сохранившийся текст из доступной истории чатов платформы, если она есть, и сразу перенести его в проект.

**Профилактика — в начале работы:**
- Хранить папку проекта в синхронизируемом хранилище или приватном репозитории (Gitea / GitHub)
- Регулярные коммиты или `git add . && git commit -m "daily snapshot"` раз в день
- Не удалять `backups/checkpoints/` без решения пользователя
- Никогда не работать с единственной локальной копией

## Сценарий 7: На защите задали вопрос, на который нет ответа

### Симптом
В процессе защиты комиссия спросила что-то, что студент действительно не знает.

### Тактика «не знаю»

Худший ответ: **долгая пауза + попытка импровизировать** с выдумыванием.

Нормальный ответ: **принять вопрос, обозначить границу**.

Шаблоны:

- «Это очень интересный вопрос, но в рамках настоящей работы я не проводил углублённого анализа [X]. Могу отметить, что [сказать что-то общее, что точно знаешь]. Более детальный разбор выходит за рамки объёма бакалаврской работы.»

- «Честно говоря, при проектировании я рассматривал [вариант], но не углублялся в [конкретный аспект, о котором спрашивают]. Это ограничение настоящей работы, и в перспективе [планируется / можно было бы] это проработать.»

- «Если я правильно понимаю вопрос — вы спрашиваете о [переформулировать]? Тогда могу сказать, что [частичный ответ из того, что знаешь]. Полностью этот аспект в рамках работы не покрыт.»

**Ключевые элементы:**
- Не врёшь (никогда не говори то, что не знаешь — это **убивает**)
- Признаёшь ограничение (комиссия любит честность)
- Даёшь частичный ответ из того, что точно знаешь
- Предлагаешь направление развития (показывает, что ты думаешь дальше работы)

### Лучший вариант — «защитный кубик»

До защиты (за 2-3 дня) проведи upgrade в `defense-mastery.md`: **собери 5 тем, которые точно проработал и можешь говорить уверенно**. На любой неожиданный вопрос — мягко сворачивай в эти темы.

Пример: спросили про вещь, которую ты не прорабатывал детально. Ответ: «Это интересно в контексте [твоя сильная тема], где я детально разбирал [X]. Там видно, что…» — и развивать то, что знаешь.

Это не увиливание — это демонстрация владения сильными сторонами работы. Комиссия оценивает общую картину, а не ответ на каждый конкретный вопрос.

## Сценарий 8: Doctor или аудит не пускают дальше

### Симптом

`vkr_project_doctor.py` возвращает `FAIL` или `vkr_audit.py` отказывает в команде.

### Что делать

Сначала выполнить `next_actions` из вывода doctor или
`python <SKILL_DIR>/scripts/vkr_audit.py <PROJECT_DIR> next --stage final --json`. Частые причины:

| Код | Что значит | Действие |
|---|---|---|
| `AUDIT_SNAPSHOT_STALE` | файлы изменились после снимка | `snapshot`, затем новые волны на новом снимке |
| `VALIDATION_REPORT_STALE`, `VALIDATION_ERRORS` | отчёт валидатора не от этого DOCX или в DOCX ошибки | исправить черновики, `quickstart.md` шаг 4, `validate` |
| `FINAL_DOCX_MULTIPLE` | в `final/` больше одного DOCX | лишние файлы — в `exports/` |
| `AUDIT_PRIMARY_WAVE_MISSING`, `AUDIT_BLIND_WAVE_MISSING` | нет завершённой финальной волны на текущем снимке; причины — в `details` | провести волну `plan --preset final` / `blind_regression` |
| `AUDIT_FINDINGS_OPEN`, `AUDIT_FAIL_UNCLOSED` | открыты BLOCKER/MAJOR или незакрытый `fail` | исправить, новый снимок, адресная перепроверка, новые волны |
| `SNAPSHOT_STALE` (при `record`) | проект менялся, пока шла проверка | не править проект во время run; спланировать проверку заново |
| `AUDITOR_NOT_INDEPENDENT` | тот же аудитор, `main`/`author` без `degraded_independence` | другой аудитор в отдельном контексте |
| `USER_EVIDENCE_REQUIRED` | нет ответов Test-30, данных пилота или факта пользователя | получить материалы, записать в `evidence/` |
| `AUDIT_LEGACY_RUNS` | проверки, записанные вручную до 6.33 | не засчитываются: провести через `vkr_audit.py` |

Если три волны подряд не сходятся по субъективным замечаниям `STY`, `LNG`, `LOG`, —
правила закрытия в `continuous-audit.md` → «Когда субъективные замечания не
сходятся». Готовность не заявляется, пока doctor не выдал нужный `readiness`.

## Общий принцип восстановления

При любом сценарии:

1. **Не паниковать. Спать 7+ часов.** Плохие решения делаются в 2 часа ночи.
2. **Оценить реальные сроки.** Что реально успеть за оставшееся время?
3. **Приоритизировать.** Что критично для допуска, что — для оценки?
4. **Искать помощи.** Научрук, однокурсники, этот скилл — все ресурсы на столе.
5. **Не добавлять паники.** Не писать гневных писем в ректорат, не делать резких шагов.

Большинство кризисных ситуаций ВКР решаемы. Отмена защиты — **редкий** исход. Обычно работа сдаётся, пусть и с понижением оценки.
