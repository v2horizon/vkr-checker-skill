# Workflow доработки существующего черновика ВКР

Этот файл — **критический**, когда у пользователя уже есть **написанный** черновик работы (полный или частичный) и нужно довести его до сдачи, а не писать с нуля.

Отличается от режима «с нуля» тем, что intake сокращается: тема, формат и продукт уже определены самим черновиком. Фокус переносится на: перенос текста в проект, проверку источников, переработку проблемных мест, подготовку к защите и финальный gate. Команды и ожидаемые результаты — `quickstart.md`.

## Когда применять этот файл

- У пользователя есть `.docx` с полным или частичным текстом ВКР
- Структура работы уже сформирована (введение, главы, заключение, список литературы)
- Нужно довести до сдачи: проверить формальности, оригинальность, стиль, источники, подготовить к защите

## НЕ применять, когда

- Работы ещё нет или есть только план → `writing-workflow.md` или `writing-workflow-express.md`
- Работа на раннем этапе (2-3 параграфа) — там лучше дописывать с нуля, используя `structure-project.md`
- Пользователь просит точечную помощь (один параграф, библиография) — тогда работать с конкретным запросом без проекта

## Этап 0: Проект и перенос черновика в `drafts/*.md`

Один источник истины текста — черновики `drafts/*.md`; DOCX всегда результат
сборки. Поэтому чужой или старый DOCX сначала переносится в проект:

1. Короткий intake (5–10 минут): тема, формат, срок, профиль, данные титула,
   **правила кафедры об использовании ИИ**, глубина владения продуктом. Ответы — в
   `<PROJECT_DIR>/intake.json` (схема `project-initialization.md`).
2. Создание проекта и импорт:

```bash
python <SKILL_DIR>/scripts/init_vkr_project.py <PROJECT_DIR> --config <PROJECT_DIR>/intake.json --json
python <SKILL_DIR>/scripts/import_docx.py <PROJECT_DIR> --docx <FILE> --json
```

Ожидается: код 0; разделы DOCX разложены по `drafts/annotation.md`,
`introduction.md`, `chapter-N.md`, `conclusion.md`, `appendix-N.md`; таблицы —
pipe-таблицы, код — fenced-блоки, рисунки — в `evidence/figures/`; список
литературы — записи `{"id": N, "raw_text": "…", "status": "pending"}` в
`sources.json`, ссылки `[N]` в тексте остаются числовыми. Отчёт —
`audit/import-report.json`; код 1 — есть элементы с потерей содержимого (формулы,
диаграммы Word, SmartArt, сноски), их агент переносит вручную по отчёту. Список
литературы разбирается так же, как `verify_sources.py --extract` (разорванная Enter
запись склеивается, `id` — номер в DOCX); если номера неоднозначны (номер
повторяется, абзац без номера) — код 1 со `status: "fail"`, ничего не записано:
исправь список в копии DOCX по `sources.problems` отчёта и повтори импорт. Если в
проекте уже есть текст, нужен `--force` (прежние файлы копируются в
`backups/checkpoints/<UTC>-import/`). Реестр со структурированными или
проверенными записями `--force` не заменяет: список литературы DOCX уходит в
`audit/sources-extracted.json` с предупреждением, замена — только
`import_docx.py <PROJECT_DIR> --docx <FILE> --force --replace-sources`.

3. Исходный файл пользователя храни вне `final/` — например, в `exports/` или вне
   проекта: в `final/` должен остаться только собранный `final/vkr.docx`.
4. `python <SKILL_DIR>/scripts/vkr_project_doctor.py <PROJECT_DIR> --stage prefinal --json`
   сразу покажет, чего не хватает: короткие обязательные разделы
   (`DRAFT_TOO_SHORT`, меньше 300 значимых символов), маркеры, записи реестра только
   с `raw_text` (`SOURCE_UNSTRUCTURED`), неподтверждённые источники.

**Частичный черновик и срок меньше двух недель.** После импорта недостающие
разделы дописываются в `drafts/*.md` по тактике `writing-workflow-express.md`
(режим — по таблице в `SKILL.md`), а уже написанные дорабатываются по этапам ниже.

## Последовательность действий (критичный порядок)

### Этап 1: Первичный аудит черновика (30-60 мин)

Цель: понять, в каком состоянии работа и где главные риски. На этом этапе
проверяется исходный файл пользователя; отчёты — в `exports/`:

```bash
python <SKILL_DIR>/scripts/validate_vkr.py <FILE> --profile <профиль из vkr-project.json> --json -o <PROJECT_DIR>/exports/validation-original.json
python <SKILL_DIR>/scripts/ai_detection_heuristic.py <FILE> --per-section -o <PROJECT_DIR>/exports/ai-detection-original.json
python <SKILL_DIR>/scripts/content_ownership_check.py <FILE> --sample 20 -o <PROJECT_DIR>/exports/ownership-original.json
```

Профиль валидатора — из `vkr-project.json` (`mpgu-09-project`, `mpgu-09-regular`
или `generic`). Отчёт `audit/automated-validation.json` здесь не пишется: он
относится только к собранному `final/vkr.docx` и создаётся `vkr_audit.py validate`.
JSON-отчёты — входы для независимых read-only аудиторов по `multi-agent-audit.md`;
аудиторы не исправляют документ, они передают находки основному агенту. Формы
команд, пороги и коды — `analyzers-cli.md`.

Дальше проверки идут по матрице `continuous-audit.md` с интенсивностью из
`vkr-project.json`: каждый законченный пакет изменений основного агента получает
профильную проверку, адресную перепроверку исправленных замечаний и слепую
регрессию; изменения источника, числа, пилота, технического решения, структуры или
DOCX запускают связанные роли.

**Что искать в результатах:**

*validate_vkr.py* (код 0 — ошибок нет, 1 — есть ошибки, 2 — файл не открыт) — формальные нарушения методички:
- Поля, шрифт, интервал: **критично** — без этого не примут
- Нумерация страниц, римские цифры глав: **критично**
- Личные местоимения («я», «мы»): **критично**
- Структура (есть все обязательные разделы?): **критично**
- Длины глав (слишком короткая Глава II — риск, надо дорабатывать)

*ai_detection_heuristic.py* — риск шаблонного «ИИ-звучания»:
- HIGH / CRITICAL → серьёзная переработка нужна
- MODERATE → выборочная правка проблемных абзацев
- LOW → можно двигаться к этапу 2, но не расслабляться
- `INSUFFICIENT_DATA` (код 1) → текста меньше минимума или разделы не распознаны; это не «низкий риск». В `--per-section` код 1 означает, что в выводе перечислены ненайденные (`missing_sections`) или недостаточные (`insufficient_sections`) разделы

*content_ownership_check.py* — вопросы для ownership-check (имитация защиты):
- Важнее чем кажется. Смотри по выборке — можешь ли ты ответить за 60 секунд устно на каждый вопрос?
- Если нет — не трогай эту главу без изучения её содержания

### Этап 2: Проверка всех источников (4-8 часов, в зависимости от количества)

**Это самая важная задача.** Работа с LLM почти гарантированно содержит галлюцинированные или неточные источники. На защите рецензент или член комиссии может проверить 2-3 случайные ссылки — если найдёт несуществующую, это катастрофа.

**Процесс** (подробно — `source-verification.md` → «Перенос извлечённых записей в реестр»):

1. Реестр уже создан импортом. Каждая запись только с `raw_text` раскладывается на
   поля по схеме `gost-citations.md` → «Реестр источников» (`type`, `authors`,
   `title`, выходные данные, `url`/`doi`). `id` записей, на которые текст ссылается
   числами `[N]`, не меняются; новые источники получают строковый `id` и ссылку `[@id]`.
2. Поисковые запросы и проверка:

```bash
python <SKILL_DIR>/scripts/verify_sources.py --queries <PROJECT_DIR>/sources.json
```

   Большой список делится на пакеты по 10–15 позиций; каждый пакет — независимый
   аудит `--preset sources`. Для **каждого** источника: `web_search` по автору и
   ключевым словам названия; существует ли работа, правильный ли год и выходные
   данные; для прямых цитат — текст первоисточника и страница.
3. Итог проверки записывает скрипт:

```bash
python <SKILL_DIR>/scripts/verify_sources.py --mark <PROJECT_DIR>/sources.json --id <ID> --status confirmed --method catalog --url <URL>
python <SKILL_DIR>/scripts/verify_sources.py --mark <PROJECT_DIR>/sources.json --id <ID> --status rejected --note "работа не найдена в РГБ и eLibrary"
```

4. Категории риска в русскоязычной литературе:
   - **Высокий риск галлюцинации:** конкретные журнальные статьи с номерами страниц («Педагогические измерения. 2020. № 2. С. 15–28»); статьи с российскими авторами в мало известных журналах
   - **Средний риск:** монографии российских педагогов (часто существуют, но год/издательство могут быть неверны)
   - **Низкий риск:** классические работы (Выготский, Кастельс в переводе), нормативные документы (152-ФЗ)
5. Для англоязычных источников — дополнительно Google Scholar и DOI.
6. Этап закрыт, когда
   `python <SKILL_DIR>/scripts/verify_sources.py --report <PROJECT_DIR>/sources.json`
   завершается кодом 0.

Если после правок в Word нужно сверить список литературы DOCX с реестром — инвентарь
`verify_sources.py --extract <PROJECT_DIR>/final/vkr.docx -o <PROJECT_DIR>/audit/sources-extracted.json`;
`sources.json` результатом `--extract` не заменяется.

**Ключевое правило:** если источник не подтвердился после 2-3 попыток поиска — **не оставлять в работе**. Либо найти реально существующую аналогичную работу, либо переформулировать тезис так, чтобы он не требовал этой ссылки; запись получает `rejected`, ссылки на неё убираются из черновиков.

Перед этапом 3 основной агент объединяет замечания аудиторов
(`vkr_audit.py <PROJECT_DIR> findings --open --json`), удаляет дубли, разрешает
конфликты по доказательствам и показывает пользователю план исправлений. Файлы в
`audit/` вручную не создаются и не правятся.

### Этап 3: Целевая переработка проблемных зон основным агентом

Правки вносятся только в `drafts/*.md` (и реестры), не в DOCX. По результатам этапа 1 работа делится на три категории:

**A. Абзацы, которые надо переписать целиком** (HIGH/CRITICAL риск ИИ):
- Обычно это теоретическая глава в местах, где LLM много «воды» про современные тенденции
- Переписывать с упором на вариативность структуры, индивидуальные безличные якорьки и конкретные технические детали из личного опыта

**B. Абзацы, которые надо смягчить** (MODERATE риск):
- Вставить 1-2 авторских якорька из профиля пользователя
- Добавить конкретики (версии, цифры, собственный пример)
- Разбить монотонные серии одинаковых предложений

**C. Абзацы, которые надо оставить** (LOW риск):
- Как правило, это описания собственного продукта, пилота, результатов — там естественная неровность

**После пакета правок** — сборка и проверка по `quickstart.md`, шаг 4, затем
проверка переписанного раздела:

```bash
python <SKILL_DIR>/scripts/ai_detection_heuristic.py <PROJECT_DIR>/final/vkr.docx --section chapter1 -o <PROJECT_DIR>/exports/ai-detection-chapter1.json
```

Чтобы убедиться, что переработка дала результат, а не ухудшила.

### Этап 4: Подготовка к защите (параллельно с правками)

В твоей ситуации — с готовым черновиком — защита это **главный риск**, не детектор.

1. Полный прогон content_ownership_check:
   ```bash
   python <SKILL_DIR>/scripts/content_ownership_check.py <PROJECT_DIR>/final/vkr.docx --all -o <PROJECT_DIR>/exports/ownership-questions.json
   ```

2. Честно пройти **каждый** вопрос с таймером (60 секунд устно). Что не можешь — отметить для глубокого изучения. Ответы своими словами основной агент записывает в `evidence/defense/` и вносит в `evidence/index.json` → `defense` (`defense-mastery.md`); без них роль `OWN` не пройдёт финал.

3. Особое внимание — на теоретическую главу. Если там упомянуты Брусиловский, ВанЛен, Алевен, Касначи (реальные или галлюцинированные) — ты должен **уметь** описать их вклад своими словами. Иначе на защите «расскажите, что конкретно Брусиловский предложил?» — и пауза.

4. По защите — отдельно читать `defense.md` и `defense-mastery.md`.

### Этап 5: Финальная сборка и финальный gate

Порядок — `quickstart.md`, шаги 4–6:

```bash
python <SKILL_DIR>/scripts/build_vkr.py <PROJECT_DIR>
python <SKILL_DIR>/scripts/update_docx_fields.py <PROJECT_DIR>/final/vkr.docx
python <SKILL_DIR>/scripts/clean_docx_metadata.py <PROJECT_DIR>/final/vkr.docx --in-place
python <SKILL_DIR>/scripts/vkr_audit.py <PROJECT_DIR> validate --json
python <SKILL_DIR>/scripts/vkr_audit.py <PROJECT_DIR> snapshot --json
python <SKILL_DIR>/scripts/vkr_project_doctor.py <PROJECT_DIR> --stage prefinal --json
```

Затем финальная primary-волна `--preset final` и более поздняя слепая волна новыми
аудиторами на том же снимке, и
`python <SKILL_DIR>/scripts/vkr_project_doctor.py <PROJECT_DIR> --stage final --json`.
Статус `READY_TO_SUBMIT` выдаёт только doctor; при `degraded_independence` — не выше
`READY_FOR_SUPERVISOR_REVIEW`. И checklist из `submission-checklist.md`.

Если после сборки пользователь правил `final/vkr.docx` в Word —
`python <SKILL_DIR>/scripts/import_docx.py <PROJECT_DIR> --docx <PROJECT_DIR>/final/vkr.docx --update`,
пересборка и новые проверки. Перед сборкой закрой документ в Word: открытый файл
сборка не заменяет (код 2 `OUTPUT_LOCKED`, ничего не изменено). Порядок, если
одновременно правят Word и черновики или реестр:

1. Сначала `import_docx.py --update` — пока `exports/citation-map.json` и
   `exports/build-manifest.json` относятся к сборке, из которой сделан DOCX.
2. Код 1 «список литературы в DOCX не совпадает с последней сборкой» — DOCX от
   другой сборки или список правили в Word: добавь/исправь источник в
   `sources.json` и пересобери; правки текста перенеси после этого.
3. Код 1 «черновики изменены после сборки: …» — если главная правка в черновике,
   пересобери и повтори правку в Word по новой сборке; если главная правка в Word —
   `python <SKILL_DIR>/scripts/import_docx.py <PROJECT_DIR> --docx <PROJECT_DIR>/final/vkr.docx --update --overwrite-drafts`
   (прежние черновики — в `backups/checkpoints/<UTC>-import/`).
4. `build_vkr.py <PROJECT_DIR> --content-only` проверяет черновики без DOCX и
   пишет только `exports/vkr-content-preview.json`: карту и манифест последней
   сборки он не меняет.

## Типичные ошибки на этом этапе

1. **«Источники уже написаны в черновике, наверное норм»** — нет, 30-40% скорее всего галлюцинированы. Проверять все.

2. **«Детектор показал MODERATE, я поправил один абзац»** — если MODERATE глобально, нужна системная правка, не точечная.

3. **«Я знаю свой проект, Test-30 я пройду»** — пройдёшь по Главе III. По Главам I и II — далеко не факт. Проверять надо **все** главы.

4. **«Поправлю перед самой сдачей»** — нет. Последние 3 дня должны быть на печать, подпись, вшивку. Финальная версия текста — **за неделю** до сдачи.

5. **«Поправлю прямо в Word и сдам»** — правка без `import_docx.py --update` пропадёт при следующей сборке, а изменённый после снимка DOCX не проходит doctor final.

## Временной бюджет на доработку

Ориентировочно (от реального качества черновика):

| Объём работ | Время |
|-------------|-------|
| Этап 0 (проект и импорт) | 0,5-1 час |
| Этап 1 (аудит) | 1-2 часа |
| Этап 2 (источники, 40-50 шт.) | 4-8 часов |
| Этап 3 (переработка 10-20 абзацев) | 6-10 часов |
| Этап 4 (Test-30 + defense prep) | 4-6 часов |
| Этап 5 (финальный gate) | 1-2 часа + время аудиторов |
| **ИТОГО** | **17-29 часов** |

При 10-15 часах в неделю — 2-3 недели реальной работы. Планируй исходя из этого.

## Важное отличие от «писать с нуля»

В режиме «с нуля» ИИ-агент пишет под твоим руководством. В режиме «доработка черновика» — **критически читает** и **оспаривает**. Отношение меняется: твой текст → объект критики, а не святое. ИИ-агент должен:

- Прямо говорить «этот абзац — ИИ-фраза» / «этот источник выглядит галлюцинированным»
- Задавать тебе вопросы «можешь ли ты объяснить эту мысль своими словами?»
- Предлагать **упрощения**, если видит, что сложный пассаж ты не сможешь защитить

Это более жёсткий режим взаимодействия. Но именно он нужен на этом этапе.
