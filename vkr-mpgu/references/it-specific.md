# Специфика IT-ВКР на русском языке

Этот файл — дополнение к `humanizer-techniques.md` специально для работ по IT-тематике (Game Design, VR, разработка ПО, веб-разработка, мобильные приложения, алгоритмы, ML/AI).

## Работы с каким содержанием покрывает файл

- Разработка образовательных VR/AR-приложений
- Разработка мобильных приложений (iOS/Android/кросс-платформа)
- Веб-разработка (фронтенд/бекенд/фулл-стек)
- Разработка игр (Unity, Unreal Engine)
- Алгоритмы и структуры данных
- Машинное обучение в прикладных задачах
- DevOps, инфраструктура, облачные решения
- UX/UI дизайн с реализацией

Для таких работ характерно:
- Наличие **продукта** (чаще всего — проектная ВКР, см. `structure-project.md`)
- Обилие **технических терминов** (часто англоязычных)
- Необходимость **листингов кода** в основной части или приложениях
- **Собственные диаграммы** архитектуры (UML, ER, flowchart, C4)
- **Скриншоты** интерфейса, логов, IDE
- **Проверка продукта** — по утверждённому профилю. Для `mpgu-09-project` обязателен образовательный пилот, а техническое тестирование его дополняет; для другого профиля возможен иной подтверждённый способ проверки

## Обращение с англоязычными терминами

### Общее правило

При первом упоминании — **русское описание + (англоязычный термин курсивом)**. При повторных — можно использовать только английский или устоявшийся русский эквивалент. Например:

> В приложении применяется графовая база данных *(graph database)*, конкретно — Neo4j версии 5.18. В отличие от реляционных СУБД, graph database позволяет...

### Когда калькировать, а когда оставлять английский

Правило согласовано с `requirements-precedence.md` («Русский язык IT-работы»):
основной текст пишется по-русски, в оригинальном написании сохраняются только
названия технологий, продуктов, классов, API, протоколов, команд, параметров и
фрагменты кода.

**Оставлять в оригинальном написании** (названия и идентификаторы):
- аббревиатуры и протоколы: API, SDK, IDE, URL, HTTP, REST, GraphQL, CI/CD
- продукты и сервисы: Git, GitHub, GitLab, Docker, Kubernetes, Unity
- идентификаторы из кода и документации: `ViewModel`, `docker compose`, `pull_request`

**Писать по-русски** (нарицательные понятия; английский вариант можно дать в скобках при первом упоминании):
- backend / frontend → серверная / клиентская часть
- framework, library, module, package → фреймворк, библиотека, модуль, пакет
- deployment, staging, production → развёртывание, тестовая / промышленная среда
- unit test, integration test → модульный, интеграционный тест
- pull request, merge conflict → запрос на слияние, конфликт слияния
- container → контейнер
- database → база данных (БД); operating system → операционная система (ОС)
- network → сеть; algorithm → алгоритм; optimization → оптимизация

**Пограничные** (обе формы допустимы; выбери одну и используй единообразно):
- cache → кеш / кэш
- controller → контроллер
- component → компонент
- request → запрос (но webhook, callback — как есть, если это названия механизмов конкретного API)

### Названия инструментов и технологий

**Всегда на английском, точно как пишут разработчики:**
- `React` (не «Реакт»)
- `Node.js` (не «Нод.джс»)
- `PostgreSQL` (не «Постгрес»)
- `Unity` (не «Юнити»)
- `Unreal Engine` (не «Анрил Энжин»)
- `TypeScript` (не «Тайпскрипт»)
- `Kubernetes` / `K8s`
- `Meta Quest 3`, `HTC Vive Pro 2`, `Valve Index` (VR-гарнитуры)

**Версии** — всегда точно, с буквенными метками: `Unity 6.0.28f1`, `React 19.0.0-rc.1`, `Node.js 22 LTS`.

## Листинги кода

### Когда включать в основной текст, а когда — в приложения

**В основной текст** (непосредственно в абзацы):
- Сниппеты 5-15 строк, иллюстрирующие ключевой алгоритм или идею
- Минимально необходимый для понимания фрагмент

**В приложения**:
- Листинги больше 20 строк
- Полные исходники модулей
- Конфигурационные файлы
- SQL-схемы, JSON-схемы

### Оформление листинга в тексте ВКР

Методичка листинги не описывает; в скилле принято:

1. **Моноширинный шрифт** — Consolas 11 pt, одинарный интервал (стиль `VKR Listing`)
2. **Отступ** — без красной строки, с отступом слева 1 см
3. **Подпись снизу** — «Листинг 1 — Функция вычисления позы» (12 pt, курсив, по центру)
4. **Ссылка в тексте** — «Реализация показана в листинге 1»

### Листинги в черновиках

В `drafts/*.md` листинг — строка `Листинг: Название` и fenced-блок сразу после
неё (полный формат — `references/drafts-format.md`):

````markdown
Реализация показана в листинге 1.

Листинг: Вычисление поз левого и правого глаза с учётом межзрачкового расстояния

```python
def compute_ipd_adjusted_pose(head_pose: Transform, ipd_mm: float) -> Tuple[Transform, Transform]:
    """Вычислить позы для левого и правого глаза с учётом IPD пользователя."""
    half_ipd = ipd_mm / 2000.0  # мм → метры
    left_offset = Vector3(-half_ipd, 0, 0)
    right_offset = Vector3(+half_ipd, 0, 0)
    left_eye = head_pose * Transform(left_offset, Quaternion.identity)
    right_eye = head_pose * Transform(right_offset, Quaternion.identity)
    return left_eye, right_eye
```
````

`build_vkr.py` ставит номер и подпись «Листинг 1 — …» под кодом. Внутри блока
кода маркеры (`[x]`, `{{ var }}`, `TODO`) и квадратные скобки вроде `arr[3]` не
считаются маркерами и ссылками на литературу и не переписываются. Идентификаторы
в тексте абзаца оформляются обратными кавычками: `` `XRGrabInteractable` ``
печатается моноширинным шрифтом.

Листинги длиннее 20–30 строк лучше выносить в приложение (`drafts/appendix-N.md`
с тем же синтаксисом). Для подсветки синтаксиса — скриншот из IDE как рисунок
(`![Название](evidence/figures/файл.png)`).

## Собственные диаграммы

Для IT-ВКР практически обязательны:

### UML-диаграммы

- **Use case** (варианты использования) — для анализа пользователей в главе 2
- **Class diagram** — для архитектуры кода
- **Sequence diagram** — для потока взаимодействий
- **Activity diagram** — для бизнес-процессов

**Инструменты:** draw.io, PlantUML (текстовое описание → картинка), Mermaid (встраивается в Markdown).

### Архитектурные диаграммы

- **C4 model** (Context, Container, Component, Code) — современный стандарт архитектурного описания
- Блок-схемы архитектуры (обычные прямоугольники со стрелками)
- Схемы деплоймента (контейнеры, сервисы, внешние системы)

### Специфические для предметной области

- **ER-диаграммы** для БД
- **Flowchart** для алгоритмов
- **Scene graph** для VR/игровых сцен
- **Network diagram** для сетевых архитектур
- **Wireframes** и **mockups** для UI

**Каждая диаграмма — подпись снизу:** «Рисунок 1 — Архитектура приложения в нотации C4 (контейнеры)».
В черновике диаграмма экспортируется в PNG в `evidence/figures/` и вставляется
строкой `![Архитектура приложения в нотации C4 (контейнеры)](evidence/figures/c4-containers.png)`;
номер и подпись ставит сборка. SVG, EMF и WebP в DOCX не вставляются — нужен PNG или JPEG.

## Пилотирование для IT-проекта

### Что проверяется пилотированием

Для IT-проектной ВКР пилот обычно включает:

1. **Юзабилити-тест** — реальная, указанная в работе выборка пользователей выполняет задачи; анализируются время и количество ошибок
2. **A/B-тест** — сравнение с альтернативным решением (конкурентом или более простой версией)
3. **Нагрузочное тестирование** — если применимо (веб-сервис, сервер)
4. **Эффективность** — метрики, специфичные для задачи (точность предсказания ML-модели, вовлечённость для образовательного продукта и т.п.)

### Метрики для образовательных IT-продуктов

Если проект — образовательное приложение / VR-урок / интерактивный курс:

- **SUS (System Usability Scale)** — 10-пунктный опросник, даёт оценку 0-100
- **Пред-пост тест** по предметному содержанию (до и после использования продукта)
- **CSAT** (Customer Satisfaction) — 5-балльная шкала удовлетворённости
- **NPS** (Net Promoter Score) — «порекомендуете ли друзьям?»
- **Time on task** — время выполнения задач
- **Engagement rate** — процент доведённых до конца сессий

### Количество участников пилотирования

В приложенной методичке минимум **5 человек** относится к пилотированию в
частной образовательной практике. Для других IT-проектов размер выборки
обосновывается задачей проверки и требованиями кафедры. Практические ориентиры:

- Юзабилити-тест: 5-10 пользователей (Nielsen показал, что 5 пользователей находят 85% проблем)
- Образовательный пилот: 15-30 учащихся (для сравнения с контрольной группой)
- A/B-тест онлайн-сервиса: 100+ пользователей (если есть возможность)

## Специфика техописания

### Избегать

- Избыточных объяснений базовых вещей: «HTTP — это протокол передачи гипертекста. Он используется для обмена данными в интернете...» (эту банальщину научрук вычеркнет)
- «Водянистых» абзацев-вступлений к разделам: «Прежде чем перейти к описанию технологии, рассмотрим её преимущества...»
- Списков всего подряд, вместо связного изложения: «К преимуществам React относятся: 1) Виртуальный DOM; 2) Компонентный подход; 3) Однонаправленный поток данных»

### Использовать

- **Конкретные сравнения** с аргументацией: «React выбран вместо Vue из-за большего экосистемного охвата (900 тыс. пакетов npm против 200 тыс. на момент начала работы) и наличия у команды собственного опыта с React hooks»
- **Численные характеристики** вместо эпитетов: вместо «высокопроизводительный» — «способный обрабатывать 1200 запросов в секунду при p99 latency 45 мс»
- **Собственные наблюдения и замечания**: «На практике оказалось, что при переходе с полигональной графики на воксельную просадка по FPS составила порядка 15% на Quest 2, но была полностью нивелирована на Quest 3»
- **Ссылки на официальную документацию**: «согласно спецификации OpenXR 1.1 (раздел 6.2)»

## Тоновое правило

IT-ВКР на русском балансирует на грани между:
- **Академическим стилем** (безличные конструкции, «представляется обоснованным», «получены следующие результаты»)
- **Инженерным стилем** (конкретные цифры, прагматичные решения, критика с обоснованием)

Слишком академично — работа читается «не по-айтишному», создаёт ощущение, что автор не из IT.

Слишком инженерно — жаргон, короткие предложения, блог-стиль → научрук отправит на доработку.

**Правильный баланс:**

> Существующая реализация обработки сетевых пакетов обладает рядом недостатков, которые, по наблюдениям автора, проявляются главным образом при числе одновременных подключений свыше 300. Анализ логов показал, что основным узким местом выступает не сеть, а блокировки доступа к разделяемой памяти: 73% времени ожидания приходится на три мьютекса в классе `SessionPool`. Решением стала замена блокирующей структуры данных на lock-free реализацию на основе RCU (read-copy-update), заимствованной из ядра Linux. Переработка потребовала 2,5 месяца и коснулась около 3400 строк кода.

Этот абзац содержит:
- Безличные формулировки («по наблюдениям автора», «Анализ показал», «Решением стала»)
- Конкретные цифры (300 подключений, 73% времени, 3400 строк, 2,5 месяца)
- Технические имена (RCU, lock-free, мьютекс, `SessionPool`)
- Ссылку на реальное решение (заимствование из Linux)
- Академический тон («обладает рядом недостатков», «проявляются главным образом»)

Этого и нужно добиваться.

## Особенности для Game Design / VR (специальность 09.03.02)

### Термины Game Design

- gameplay loop (игровой цикл) — основная петля взаимодействия
- progression system (система прогрессии) — как растёт игрок
- game feel (ощущение игры) — субъективное качество управления
- onboarding — введение в игру для новичков
- metagame — стратегии поверх базовой механики
- monetization (модель монетизации) — F2P, premium, season pass и т.д.
- retention (удержание) — метрика возвращаемости

### VR-специфика

Обязательные для упоминания при работе с VR:

- **IPD (interpupillary distance)** — межзрачковое расстояние
- **Foveated rendering** — отрисовка с учётом направления взгляда
- **Motion sickness / VR sickness** — кинетоз, побочный эффект VR
- **Tracking** — inside-out (камеры на гарнитуре) vs outside-in (внешние датчики)
- **6DoF / 3DoF** — шесть / три степени свободы
- **Haptic feedback** — тактильная обратная связь

Эти термины встречаются редко в общих русскоязычных текстах и заметно повышают уникальность.

### Ключевые источники для IT/VR-ВКР (проверенные, реальные)

Для грамотной работы с источниками полезно знать основные академические/индустриальные площадки:

- **IEEE Xplore** — основная база по computer science
- **ACM Digital Library** — особенно CHI (Conference on Human Factors in Computing Systems) по HCI/VR
- **arXiv.org** — препринты, особенно cs.GR (графика), cs.HC (HCI)
- **Google Scholar** — обобщённая площадка
- **Scopus / WoS** — для академического авторитета
- **CyberLeninka / eLibrary** — для российских работ

Для индустриальных данных:
- **Newzoo, Statista** — статистика по играм и VR
- **Meta Research, NVIDIA Research** — корпоративные публикации
- **Khronos OpenXR spec** — официальная спецификация OpenXR
- **Unity docs, Unreal Engine docs** — источники о движках
