# Формат черновиков `drafts/*.md`

Текст ВКР живёт в черновиках Markdown. DOCX — всегда результат сборки:

```text
python <SKILL_DIR>/scripts/build_vkr.py <PROJECT_DIR>
```

Команда читает `vkr-project.json`, `drafts/*.md` и `sources.json`, пишет
`exports/vkr-content.json`, `exports/citation-map.json` и единственный сдаваемый
файл `final/vkr.docx`. Прежний `final/vkr.docx` сохраняется в
`backups/checkpoints/<UTC>-build/`. Правки, сделанные в Word, возвращаются в
черновики командой `import_docx.py --update` (раздел «Импорт» ниже).

Порядок записи: сначала сборка проверяет, что `final/vkr.docx` и служебные файлы
можно перезаписать (DOCX открыт в Word — код 2 `OUTPUT_LOCKED`, ничего не
изменено: закрой файл и повтори); DOCX пишется во временный файл и атомарно
подменяется; только после этого пишутся `exports/build-manifest.json`,
`exports/citation-map.json` и `exports/vkr-content.json` с общим `build_id`.
Карта хранит номер → `id` (`numbers`: `{"1": "ivanov2020", …}` — направление
обратное карте `format_bibliography.py --mapping`, где `id` → номер) и текст записи
списка под каждым номером (`entries`): по ним `import_docx.py --update` сверяет
список литературы DOCX. Предупреждения сборки (`SOURCE_NOT_CITED`, `RENDER` и
др.) повторяются в `exports/build-manifest.json` → `warnings`, чтобы их видел и
новый чат.

## Файлы и порядок сборки

| Файл | Раздел DOCX | Обязателен |
|---|---|---|
| `drafts/annotation.md` | Аннотация (не входит в содержание) | да |
| `drafts/introduction.md` | Введение | да |
| `drafts/chapter-1.md` … `chapter-N.md` | Глава I … Глава N (по номеру файла) | профиль `mpgu-09-project`: главы 1–3; остальные профили: не меньше двух |
| `drafts/conclusion.md` | Заключение | да |
| — | Список использованной литературы (из `sources.json`) | создаётся сборкой |
| `drafts/appendix-1.md` … | Приложение 1 … (по номеру файла) | нет |

Главы нумеруются подряд: пропуск номера (`chapter-1.md`, `chapter-3.md`) —
ошибка. Другие файлы в `drafts/` в сборку не входят (предупреждение).
Черновик, в котором нет текста кроме заголовков и комментариев, считается
пустым: для обязательного раздела это ошибка.

Титульный лист собирается из `vkr-project.json` → `topic` и `title_page`
(университет, институт, кафедра, код и название направления, профиль, автор,
группа, научный руководитель, заведующий кафедрой, город, год). Пустое поле
печатается на титуле маркером `[ЗАПОЛНИТЬ: …]`, сборка выдаёт предупреждение.

## Заголовки

- `# Заголовок` — первая строка файла. Во введении, заключении и аннотации текст
  заголовка не важен: в DOCX пишется «Введение», «Заключение», «Аннотация».
- В главе номер берётся из имени файла. Префикс `Глава I.` писать не обязательно;
  если он есть, сборка его убирает (в DOCX никогда не будет «Глава I. Глава I.»).
- В приложении `# Название приложения`; префикс `Приложение 1.` тоже убирается,
  метка «Приложение N» ставится по номеру файла.
- `## Название` или `## 1.1. Название` — параграф главы. Номер `1.1.`
  проставляет сборка по порядку; несовпадающий номер в черновике — предупреждение.
- `## Выводы по главе` (или `## Выводы по главе I`) — выводы главы; в DOCX
  печатаются «Выводы по главе I» в конце главы.
- `###` и глубже не поддерживаются: такая строка печатается обычным абзацем.
  Во введении, заключении, аннотации и приложениях `##` тоже печатается абзацем.

```markdown
# Глава I. Теоретические основы применения VR в обучении

Вводный абзац главы до первого параграфа.

## Пространственное мышление учащихся

Текст параграфа.

## Выводы по главе

Выводы.
```

## Абзацы и строчный код

Абзацы разделяются пустой строкой. Одиночный перевод строки внутри абзаца —
пробел, поэтому длинные абзацы можно переносить как удобно. Фрагмент в обратных
кавычках `` `XRGrabInteractable` `` печатается моноширинным шрифтом без кавычек;
внутри него маркеры и ссылки не распознаются.

HTML-комментарии `<!-- … -->` в DOCX не попадают. Комментарии, начинающиеся с
«Черновик» или «Заполняется», — маркеры незавершённого текста.

## Списки

```markdown
Задачи исследования:

1. проанализировать литературу;
2. разработать прототип;
3. провести пилотирование.

1. первый пункт следующего списка;
2. второй пункт.

- маркированный пункт;
- ещё пункт.
```

- Пункт — строка `- текст`, `* текст` или `1. текст` / `1) текст`. Следующая
  строка без маркера и без пустой строки продолжает пункт.
- Каждый нумерованный список в DOCX начинается с 1. Новый список начинается
  после абзаца текста, после пустой строки, если следующий номер не
  продолжает предыдущий (например, снова `1.`), или со строки `1.` сразу
  после пунктов `2.`, `3.`.
- Пункты оформляются стилем `List Paragraph` с автоматической нумерацией,
  по ширине, с висячим отступом. Вложенные списки не поддерживаются: пункт с
  отступом печатается на первом уровне (предупреждение).

## Таблицы

```markdown
Таблица: Сравнение VR-платформ для школы

| Критерий | Unity XR | WebXR |
|---|---|---|
| Порог входа | средний | низкий |

Источник: составлено автором по [@unity-docs]
```

- Строка `Таблица: Название` стоит непосредственно перед таблицей (пустая
  строка между ними допустима). Номер «Таблица N» сквозной, его ставит сборка.
  Таблица без подписи — предупреждение: методичка требует заголовок.
- Первая строка до разделителя `|---|` — заголовки столбцов.
- `Источник: …` — отдельной строкой сразу после таблицы (можно через пустую
  строку); ссылки в ней пересчитываются как в тексте.
- Символ `|` внутри ячейки пишется как `\|`.

## Листинги

````markdown
Листинг: Проверка ответа ученика

```csharp
public bool Check(int[] answers) {
    return answers[0] == expected;
}
```
````

- Строка `Листинг: Название` перед fenced-блоком; номер и подпись
  «Листинг N — Название» под кодом ставит сборка.
- Код печатается стилем `VKR Listing` (Consolas 11, одинарный интервал).
- Внутри блока кода маркеры (`[x]`, `{{ var }}`, `TODO`) и ссылки (`[3]`,
  `[@id]`) не распознаются и не переписываются.
- Блок без строки `Листинг:` тоже становится листингом, но без подписи
  (предупреждение). Незакрытый блок — ошибка.
- Длинный код лучше выносить в приложение (`appendix-N.md`).

## Рисунки

```markdown
![Архитектура тренажёра](evidence/figures/architecture.png)

![Экран результатов пилотирования]()
```

- Путь — относительно корня проекта, файлы рисунков лежат в
  `evidence/figures/`. Вставляются PNG, JPEG, GIF, BMP, TIFF; SVG, EMF и WebP
  нужно экспортировать в PNG. Ширина уменьшается до области текста (165 мм).
- Отсутствующий файл или путь вне проекта — ошибка сборки.
- Пустой путь `![Название]()` — заглушка `[ Здесь вставить рисунок вручную в Word ]`.
  Это маркер незавершённого текста: на стадии final его быть не должно.
- Подпись «Рисунок N — Название» под рисунком и сквозной номер ставит сборка.

## Ссылки на источники

Каждый источник описан в `sources.json` (схема — `gost-citations.md`, раздел
«Реестр источников»). В тексте на него ссылаются по `id`:

| Черновик | DOCX (пример) | Когда |
|---|---|---|
| `[@ivanov2020]` | `[4]` | ссылка без страницы |
| `[@ivanov2020, с. 23]` | `[4, с. 23]` | цитата со страницей |
| `[@ivanov2020, с. 23–25]` | `[4, с. 23–25]` | диапазон страниц |
| `[@smith2019, p. 105]` | `[8, p. 105]` | иностранный источник |
| `[@ivanov2020; @petrov2021]` | `[4; 6]` | несколько источников |
| `[Цит. по: @ivanov2020, с. 5]` | `[Цит. по: 4, с. 5]` | цитата не по первоисточнику |
| `[3, с. 17]` | `[7, с. 17]` | legacy: источник с целым `id` 3 |

- Сборка сортирует список литературы по алфавиту (правило — `gost-citations.md`)
  и переписывает все ссылки в итоговые номера. Номера вручную не расставляются.
  В ссылке на несколько источников номера идут по возрастанию: `[@petrov2021;
  @ivanov2020]` → `[4; 6]` (страница остаётся при своём номере, общий префикс
  «см.», «Цит. по:» — в начале).
- `id` — латинские буквы, цифры и `_ . : -`, либо целое число. Удобно
  `фамилия+год`: `ivanov2020`, `unity-docs`.
- Ошибки сборки (код 1, DOCX не перезаписывается): ссылка на `id`, которого
  нет в реестре; процитирован источник со `status: "rejected"`; процитирована
  запись только с `raw_text` (не разобрана на поля) или запись, которую нельзя
  оформить (нет обязательных полей).
- Предупреждения: источник реестра не процитирован (методичка требует, чтобы
  список и текст соответствовали друг другу — такой источник всё равно
  попадает в список); процитирован источник со статусом `pending` или
  `suspicious`; ссылка в заключении (методичка: заключение без ссылок и цитат).
- Записи `rejected` в список не попадают; непроцитированная запись только с
  `raw_text` пропускается с предупреждением.

## Что проверяет сборка

| Код | Уровень | Что значит |
|---|---|---|
| `DRAFT_REQUIRED_MISSING`, `DRAFT_EMPTY`, `DRAFT_CHAPTER_GAP` | ошибка | нет обязательного черновика, он пуст или пропущен номер главы |
| `CHAPTER_TITLE_MISSING`, `APPENDIX_TITLE_MISSING`, `TOPIC_MISSING`, `AUTHOR_MISSING` | ошибка | нет заголовка главы/приложения, темы или автора |
| `SOURCE_UNKNOWN`, `SOURCE_REJECTED`, `SOURCE_UNSTRUCTURED`, `SOURCE_INVALID`, `SOURCE_ID_DUPLICATE` | ошибка | ошибки ссылок и реестра |
| `FIGURE_NOT_FOUND`, `FIGURE_OUTSIDE_PROJECT`, `FIGURE_FORMAT`, `CODE_BLOCK_UNCLOSED` | ошибка | рисунок или код нельзя вставить |
| `MARKER` | предупреждение | маркер незавершённого текста вне кода (`[ПРОВЕРИТЬ]`, `[ЗАПОЛНИТЬ: …]`, `{{…}}`, `TODO`, `[Название]`…) |
| `SOURCE_NOT_CITED`, `SOURCES_NOT_CONFIRMED`, `SOURCE_SKIPPED`, `CITATION_IN_CONCLUSION` | предупреждение | соответствие списка и текста |
| `SOURCE_VERIFICATION_MISSING`, `SOURCE_STATUS_UNKNOWN` | предупреждение | у процитированного `confirmed`-источника нет `verification {method, checked_at, url\|note}` или у записи нет статуса; на стадии final doctor считает это ошибкой |
| `SOURCE_VERIFICATION_STALE` | предупреждение | реквизиты процитированного `confirmed`-источника изменены после `verify_sources.py --mark` (`verification.fields_sha256` не совпадает): сверь запись и отметь заново |
| `OUTPUT_LOCKED`, `IO_ERROR` | ошибка, код 2 | `final/vkr.docx` или служебный файл сборки открыт в Word (другой программе) или защищён от записи; проверка идёт до любых записей — ничего не изменено |
| `TABLE_NO_CAPTION`, `PARAGRAPH_NUMBER_MISMATCH`, `LIST_NESTED`, `HEADING_LEVEL_UNSUPPORTED`, `RENDER` | предупреждение | оформление |
| `FINAL_OTHER_DOCX` | предупреждение | в `final/` лежат другие DOCX — сдаётся один `final/vkr.docx` |

```text
python <SKILL_DIR>/scripts/build_vkr.py <PROJECT_DIR> [--json] [-o REPORT]
       [--output final/vkr.docx] [--content-only] [--group-normative-first]
```

Коды: 0 — собрано (предупреждения допустимы); 1 — ошибки содержания, файлы не
перезаписаны; 2 — ошибка использования, чтения или записи файлов (в том числе
`OUTPUT_LOCKED`: DOCX открыт в Word — закрой его и повтори, ничего не изменено)
или нет python-docx.
`--json` печатает отчёт `{status, exit_code, build_id, outputs, stats, errors, warnings, next_steps}`,
`-o` сохраняет его в файл. `--content-only` — проверка содержания без DOCX: пишет
только `exports/vkr-content-preview.json`; `exports/citation-map.json`,
`exports/build-manifest.json` и `exports/vkr-content.json` описывают последний
собранный `final/vkr.docx` и не меняются (иначе `import_docx.py --update`
сверял бы правки Word с чужой нумерацией).
После сборки `final/vkr.docx` сборка сама называет следующие шаги (`next_steps`
с готовыми командами):

1. `update_docx_fields.py <PROJECT_DIR>/final/vkr.docx` — оглавление и поля через
   Word; код 1 (Word недоступен) — открыть файл в Word, Ctrl+A, F9, сохранить;
2. `clean_docx_metadata.py <PROJECT_DIR>/final/vkr.docx --in-place`;
3. `vkr_audit.py <PROJECT_DIR> validate`.

Сборка в другой путь (`--output exports/…`) — промежуточный файл: шагов нет,
содержание пишется в `exports/vkr-content-preview.json`, карта, манифест и
`exports/vkr-content.json` последней сборки `final/vkr.docx` не меняются.

## Импорт готового DOCX

```text
python <SKILL_DIR>/scripts/import_docx.py <PROJECT_DIR> --docx <FILE> [--update] [--overwrite-drafts] [--force] [--replace-sources] [--json] [-o REPORT]
```

- Без `--update` — перевод чужого или старого DOCX в проект после init. Титул,
  содержание и последний лист с клятвой пропускаются; разделы раскладываются по
  черновикам; код (стиль `VKR Listing` или моноширинный шрифт) становится
  fenced-блоками (пустые абзацы между моноширинными строками — пустые строки того
  же листинга; если листинг всё же разорван абзацем обычного шрифта —
  предупреждение), таблицы — pipe-таблицами, рисунки сохраняются в
  `evidence/figures/`, списки — `-`/`1.`. Список литературы становится
  `sources.json` с записями `{"id": N, "raw_text": "…", "status": "pending"}`,
  ссылки `[N]` остаются числовыми (legacy). Записи разбираются той же функцией,
  что у `verify_sources.py --extract`: запись, разорванная Enter, склеивается,
  `id` — номер записи в DOCX. Если номера неоднозначны — номер повторяется, абзац
  без номера не похож ни на продолжение, ни на подзаголовок, часть записей
  пронумерована текстом, часть автонумерацией Word, — код 1, `status: "fail"`,
  причины в `sources.problems`, ничего не записано: исправь список в копии DOCX и
  повтори импорт. Перед сборкой записи реестра нужно разобрать на поля. Если в
  проекте уже есть текст, нужен `--force` (прежние файлы копируются в
  `backups/checkpoints/<UTC>-import/`).
- `--force` не заменяет реестр, в котором есть структурированные записи или
  статусы `confirmed`/`suspicious`/`rejected` (то же правило, что у
  `verify_sources.py --extract`): `sources.json` остаётся, список литературы DOCX
  пишется в `audit/sources-extracted.json` (`{id, raw_text, status, hints}`), в
  отчёте — предупреждение и `sources.registry_preserved`. Ссылки `[N]` в новых
  черновиках — номера этого списка, а не `id` реестра: сверь их по
  `source-verification.md` → «Перенос извлечённых записей в реестр». Заменить такой
  реестр записями `raw_text` — только `--force --replace-sources` (прежний
  `sources.json` — в той же резервной копии).
- `--update` — после ручной правки собранного `final/vkr.docx` в Word. Изменённые
  блоки (абзацы, списки, таблицы, листинги, заголовки) переносятся в черновики,
  неизменённые остаются как были — с комментариями и переносами строк. Числа
  `[N]` превращаются обратно в `[@id]` по `exports/citation-map.json`;
  `sources.json` не меняется, правки списка литературы в Word не переносятся.
  До записи две проверки, при отказе — код 1, `status: "fail"`, черновики не
  изменены:
  1. Список литературы DOCX сверяется с `entries` карты последней сборки
     (нормализованный текст по номерам). Расхождение значит, что DOCX собран
     другой сборкой или список правили в Word: номера `[N]` указали бы не на те
     источники. Порядок: добавь или исправь источник в `sources.json` и
     пересобери; правки текста перенеси после этого (прежний DOCX с правками —
     в `backups/checkpoints/<UTC>-build/vkr.docx`).
  2. Черновики, которые импорт перезаписал бы, сверяются с хешами
     `exports/build-manifest.json` той же сборки (`build_id`). Черновик изменён
     после сборки — в отчёте `drafts_changed_after_build` со списком файлов. Если
     главная правка в черновике — пересобери DOCX и повтори правку в Word; если
     главная правка в Word — повтори импорт с `--overwrite-drafts` (прежние
     черновики уйдут в `backups/checkpoints/<UTC>-import/`). Правки, записанные
     прошлым `--update` этой же сборки, конфликтом не считаются
     (`exports/import-sync.json`); отсутствующий черновик создаётся заново из DOCX.
- Отчёт всегда пишется в `audit/import-report.json`: созданные и обновлённые
  файлы, пропущенные части, нераспознанные элементы. Код 1 бывает двух видов:
  `status: "fail"` — импорт остановлен проверкой (см. выше), ничего не записано;
  `status: "incomplete"` — импорт выполнен, но есть элементы с потерей содержимого
  (формулы, диаграммы Word, SmartArt, сноски, рисунки в таблицах): их нужно
  перенести вручную.
