# Анализаторы текста ВКР: справка по командам

Два анализатора читают собранный DOCX (обычно `<PROJECT_DIR>/final/vkr.docx`) и
ничего в нём не меняют:

- `ai_detection_heuristic.py` — эвристический риск «похоже на ИИ-текст»
  (burstiness, клише, лексика, ритм, пассив, местоимения). Это самопроверка, а не
  симуляция Антиплагиат.Вуз: LOW не гарантирует прохождение детектора.
- `content_ownership_check.py` — вопросы комиссии по абзацам работы для
  подготовки к защите.

Проверка источников (`verify_sources.py`) описана в
[source-verification.md](source-verification.md).

Нужен Python 3.9+ и `python-docx`; `--help` работает и без него. Отчёты кладутся в
`<PROJECT_DIR>/exports/`.

## Что анализируется

Оба скрипта одинаково делят документ на разделы.

1. **Заголовки разделов.** Абзацы со стилем `Heading 1`/`Heading 2`
   («Заголовок 1/2») или уровнем структуры; если стилей нет — отдельные абзацы,
   целиком совпадающие с названием раздела: «Введение», «Глава I…» / «Глава 1.
   …» (номер арабский, римский или словом; длина названия не ограничена),
   «Заключение», варианты заголовка списка литературы («Список использованной
   литературы», «Список использованных источников», «Список литературы»,
   «Библиографический список», «Литература», «… и источников»), «Приложение N»,
   «Приложения». Регистр, «ё/е» и точка или двоеточие в конце не важны.
2. **Что не обрывает раздел.** Обычный абзац или пункт списка, который лишь
   начинается со слов «Список», «Приложение», «Библиограф…» («Список требований
   к тренажёру сформирован…», «Приложение разработано на Unity…»), подзаголовки
   параграфов («1.1. …»), строка «Выводы по главе I». «Глава II» не совпадает с
   «Глава I».
3. **Главы без слова «Глава».** Если в документе нет ни одного заголовка
   «Глава N», заголовки `Heading 1` между введением и заключением («1.
   Теоретические основы…») считаются главами по порядку — введение их не
   поглощает.
4. **Исключается из анализа:** титульный лист (всё до первого раздела),
   аннотация, содержание (стили TOC, поле TOC, sdt-оглавление, строки
   «Название<TAB>34» и с точками-заполнителями), список литературы, приложения,
   последний лист с клятвой, код (стиль `VKR Listing` или моноширинный шрифт),
   подписи (`VKR Caption`, «Таблица N», «Рисунок N — …», «Листинг N — …»,
   «Источник: …»), заголовки и абзацы стиля `VKR Title`.
5. **В анализ идут** введение, все главы и заключение. Если ни один раздел не
   распознан, анализируется весь текст без перечисленных служебных областей
   (включая ячейки таблиц для детектора ИИ), а отчёт помечает это
   `"structure": "unrecognized"`.

Имена разделов в командах: `introduction`, `chapter1`, `chapter2`, … `chapterN`,
`conclusion`.

## `ai_detection_heuristic.py`

```bash
python <SKILL_DIR>/scripts/ai_detection_heuristic.py <PROJECT_DIR>/final/vkr.docx
python <SKILL_DIR>/scripts/ai_detection_heuristic.py <PROJECT_DIR>/final/vkr.docx --section chapter1
python <SKILL_DIR>/scripts/ai_detection_heuristic.py <PROJECT_DIR>/final/vkr.docx --per-section -o <PROJECT_DIR>/exports/ai-detection-sections.json
python <SKILL_DIR>/scripts/ai_detection_heuristic.py <PROJECT_DIR>/final/vkr.docx --json -o <PROJECT_DIR>/exports/ai-detection.json
```

| Режим | Что делает | Минимум текста |
|---|---|---|
| без флагов | весь основной текст: введение + главы + заключение, стандартные пороги | 300 слов |
| `--section NAME` | один раздел со своими весами и порогами | 120 слов |
| `--per-section` | введение, каждая найденная глава и заключение отдельно | 120 слов на раздел |

`--section` и `--per-section` вместе не указываются.

**Уровни риска** (`risk.risk_level`): `LOW`, `MODERATE`, `HIGH`, `CRITICAL` по
баллу `risk.risk_score` (0–100) и порогам раздела:

| Раздел | LOW < | MODERATE < | HIGH < | иначе |
|---|---|---|---|---|
| весь текст, `chapter2`, главы после третьей | 20 | 40 | 60 | CRITICAL |
| `introduction`, `conclusion` | 18 | 36 | 55 | CRITICAL |
| `chapter1` (теория — мягче) | 25 | 48 | 68 | CRITICAL |
| `chapter3` (проект — строже по весам) | 22 | 42 | 62 | CRITICAL |

`INSUFFICIENT_DATA` — текста меньше минимума: `risk_score` = `null`, в `flags`
написано, сколько слов найдено. Это не «низкий риск»: добавь текст или проверь,
что разделы распознаны (`meta.sections_found`).

**JSON** (`--json` или `-o`):

- обычный режим и `--section`: ключи метрик (`burstiness`, `ngrams`, `lexical`,
  `anchors`, `pronouns`, `rhythm`, `starters`, `passive`, `readability`), `risk`,
  `status` (`ok` | `insufficient_data` | `section_not_found` | `error`),
  `exit_code` и `meta` (`structure`, `sections_found`, `sections_analyzed`,
  `words`, `paragraphs`, `cliche_allowlist`);
- `--per-section`: `status` (`ok` | `incomplete` | `insufficient_data`),
  `sections` (`{имя: результат с risk, words, paragraphs}`), `missing_sections`
  (ожидаемые, но не найденные разделы: введение, заключение и пропуски в номерах
  глав), `insufficient_sections` (найдены, но меньше 120 слов), `meta`.

**Коды выхода**

| Код | Когда |
|---|---|
| 0 | анализ выполнен (любой уровень риска); в `--per-section` найдены все ожидаемые разделы и в каждом достаточно текста |
| 1 | `INSUFFICIENT_DATA`; раздел `--section` не найден; в `--per-section` есть `missing_sections` или `insufficient_sections` (они перечислены в выводе) |
| 2 | нет файла, повреждённый DOCX, нет python-docx, неверное имя раздела, не удалось записать `-o` или `-o` указывает внутрь каталога скилла |

## `content_ownership_check.py`

```bash
python <SKILL_DIR>/scripts/content_ownership_check.py <PROJECT_DIR>/final/vkr.docx
python <SKILL_DIR>/scripts/content_ownership_check.py <PROJECT_DIR>/final/vkr.docx --section chapter3
python <SKILL_DIR>/scripts/content_ownership_check.py <PROJECT_DIR>/final/vkr.docx --all -o <PROJECT_DIR>/exports/ownership-questions.json
```

- Вопросы строятся по абзацам не короче 80 символов из введения, глав и
  заключения (правила выше). Список литературы, аннотация, титул, код и подписи в
  вопросы не попадают; в вопросах нет шаблонных подстановок вида «{X}».
- **Выборка по умолчанию:** 25 случайных абзацев (`--sample N`, `0` — без
  выборки). Отчёт явно помечен: в тексте строка «ВЫБОРКА: 25 из 47 абзацев
  (seed 42). Полный прогон: --all», в JSON — `"sampling": "sample"`,
  `sample_size`, `available_paragraphs`, `seed`, `sampling_note`.
- **`--all`** — полный прогон всех абзацев (`"sampling": "all"`); используй его
  перед защитой.
- **Воспроизводимость:** одинаковые файл, `--sample` и `--seed` (по умолчанию 42)
  дают одинаковый отчёт; выбранные абзацы идут в порядке документа,
  `items[].paragraph_id` — номер абзаца в полном списке, `items[].section` — раздел.
- `--section NAME` — только раздел; типы вопросов подбираются под раздел
  (вопросы о пилотировании — только для `chapter3` и т. п.). Без `--section`
  применяются все типы вопросов.
- `--full` — печатать абзацы целиком. `--per-section` у этого скрипта нет.

**Коды выхода:** 0 — вопросы сформированы; 1 — раздел `--section` не найден
(`"status": "section_not_found"`) или нет ни одного абзаца не короче 80 символов
(`"status": "insufficient_data"`, `"risk_level": "INSUFFICIENT_DATA"`); 2 — нет
файла, повреждённый DOCX, нет python-docx, неверные аргументы, ошибка записи `-o`.

## Персональный `cliche_allowlist`

Оба скрипта одинаково читают `cliche_allowlist` из `vkr-state.md` (также
`.vkr-state.md`): ищут в каталоге DOCX и выше, не больше трёх уровней и не выше
каталога, в котором лежит `vkr-project.json` (state-файл другого проекта не
подхватывается). Для `final/vkr.docx` это `<PROJECT_DIR>/vkr-state.md`.

Поддерживаемые формы (фразы сравниваются без учёта регистра и «ё/е»):

```yaml
cliche_allowlist:
  - "стоит отметить"
  - "в современном мире"
```

```yaml
cliche_allowlist:
- "стоит отметить"
- в современном мире   # комментарий допускается
```

```yaml
cliche_allowlist: ["стоит отметить", "в современном мире"]
```

`cliche_allowlist: []` и закомментированные строки `# cliche_allowlist:` означают
пустой список.

- `ai_detection_heuristic.py` не считает фразы из списка ИИ-клише.
- `content_ownership_check.py` не считает фразу из списка маркером вопроса
  (например, «следует отметить» перестаёт порождать вопрос о позиции автора).
- Оба пишут в JSON `cliche_allowlist: {state_file, phrases}`, текстовый отчёт
  сообщает об активном списке.

## Вывод, файлы и кодировка

- Без флагов — текстовый отчёт в stdout; `--json` — только JSON в stdout.
- `-o FILE` — JSON-отчёт в файл (UTF-8 без BOM, каталоги создаются); текстовый
  отчёт при этом всё равно печатается, если не указан `--json`. Файл внутри
  каталога скилла не пишется (код 2) — отчёты кладутся в `<PROJECT_DIR>/exports/`.
- Скрипты всегда пишут в консоль UTF-8. В Windows PowerShell 5.1 перехват вывода
  (`$x = python …`) или перенаправление `> файл` в OEM-кодировке консоли
  превращает кириллицу в «╨Я╨╡…». Надёжный способ — `-o FILE` и чтение файла.
  Для перехвата текста сначала выполни
  `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`.
