# Автоматические контрольные точки независимого аудита

Этот файл определяет, **когда основной ИИ-агент запускает независимых read-only
аудиторов и какими командами он это делает**. Роли, доказательства и формат
отчёта описаны в `multi-agent-audit.md`.

Основной агент остаётся единственным автором и редактором ВКР. Аудиторы только
возвращают отчёты. Служебные записи аудита — снимок, хеши, задачи, попытки,
`execution_id`, метки времени, номера замечаний — пишет `vkr_audit.py`. Агент
не заполняет эти поля руками и не редактирует файлы в `audit/`.

Во всех командах `<SKILL_DIR>` — абсолютный путь к установленному скиллу,
`<PROJECT_DIR>` — абсолютный путь к проекту. Коротко:

```bash
A="python <SKILL_DIR>/scripts/vkr_audit.py <PROJECT_DIR>"
```

## Интенсивность

`audit_intensity` хранится в `vkr-project.json` (канонично) и дублируется в
разделе «Независимый аудит» state-файла:

- `balanced` — аудит после intake, плана, пакета источников, продукта, пилота,
  главы, введения, заключения, аннотации, полного черновика, DOCX, пакета
  правок и финала; подраздел проверяется только при событии высокого риска;
- `strict` — дополнительно каждый завершённый подраздел (роль `STY` — в каждом
  втором) и B-реплики `MET`, `LOG`, `SRC`, `EVD`, `TEC`, `DOC` в финальной волне;
- `maximum` — как `strict`, но A/B-реплики у всех ключевых ролей глав и две
  реплики каждой из девяти ролей в обеих финальных волнах.

`init_vkr_project.py` ставит `strict` для режима `standard` и `balanced` для
`express-*`; явный выбор пользователя сохраняется. Пользователь может сменить
интенсивность в любой момент: исправь `vkr-project.json` и state одним
checkpoint. `audit_autorun` по умолчанию равен `true`.

## Устойчивая контрольная точка

Аудит запускается после сохранения законченного смыслового результата:
заполненного intake, утверждённого плана, завершённого подраздела (обычно
1200–2000 слов), главы, введения, заключения или аннотации, пакета из 10–15
источников, описания продукта, расчёта или пилота, новой сборки DOCX, пакета
исправлений, предфинальной и финальной версии. Не прерывай генерацию посреди
абзаца или подраздела.

## Роли и линзы

Базовые роли: `MET` — методичка и профиль; `SRC` — источники, реквизиты,
цитаты и поддержка тезисов; `LOG` — научная логика; `LNG` — язык; `STY` —
академический стиль и ИИ-паттерны; `EVD` — доказательства чисел, пилота и
результатов; `TEC` — техническая корректность продукта; `DOC` — DOCX и
нормоконтроль; `OWN` — владение материалом и вопросы защиты.

Каждая задача раскладывается на `auditor_role`, `base_gate` и `audit_lens`:

| `auditor_role` | `base_gate` | `audit_lens` |
|---|---|---|
| базовая роль (`MET` … `OWN`) | та же | `full_gate` |
| `SRC-BIB` | `SRC` | `bibliography` |
| `SRC-CIT` | `SRC` | `claim_support` |
| `SRC-CROSSREF` | `SRC` | `cross_references` |
| `DOC-STRUCTURE` | `DOC` | `structure` |
| `DOC-VISUAL` | `DOC` | `visual_render` |
| `MET-FORMAT` | `MET` | `format_requirements` |
| `OWN-QUESTIONS` | `OWN` | `question_generation` |
| `OWN-DEFENSE` | `OWN` | `interactive_defense` |

Линза специализированной роли закрывает только свою область. Финальную волну
закрывают только задачи базовых ролей с `full_gate`; специализированные роли
можно добавить к ней, но они не заменяют базовую.

Реплики одной роли (`A`, `B`, в слепой волне `C`, `D`) — это разные аудиторы в
отдельных контекстах с одной линзой и разным порядком проверки `review_order`:
`forward` и `backward` для `MET`, `LOG`, `LNG`, `STY`, `DOC`, `OWN`;
`evidence_first` и `adversarial` для `SRC`, `EVD`, `TEC`. Порядок и линзу
назначает `plan`; реплика не видит отчёт другой реплики.

## Матрица и пресеты

Каждой строке соответствует `plan --preset`. Команда сама раскрывает роли с
учётом `audit_intensity` и `vkr_type`.

| Событие | Команда | Роли (`strict`) |
|---|---|---|
| Intake завершён | `plan --kind primary --preset intake` | `MET`, `EVD`, `TEC` |
| План сформирован или изменён | `--preset plan` | `MET`, `LOG-A`, `LOG-B`, `EVD`, `TEC` |
| Подраздел завершён | `--preset subsection --checkpoint subsection-2.3` | `LOG`, `SRC`, `LNG`; `STY` в каждом втором |
| Подраздел содержит код или архитектуру | `--preset subsection --replicas TEC=A,B` | базовый набор плюс `TEC-A`, `TEC-B` |
| Подраздел содержит числа или результаты | `--preset subsection --replicas EVD=A,B` | базовый набор плюс `EVD-A`, `EVD-B` |
| Новая или заменённая ссылка | `--preset custom --roles SRC-BIB,SRC-CIT` | `SRC-BIB`, `SRC-CIT` |
| Добавлена прямая цитата | `--preset custom --replicas SRC=A,B` | `SRC-A`, `SRC-B` |
| Пакет 10–15 источников | `--preset sources` | `SRC-BIB-A`, `SRC-BIB-B`, `SRC-CIT` |
| Закончено описание продукта | `--preset product` | `TEC-A`, `TEC-B`, `EVD`, `LOG`, `OWN-QUESTIONS` |
| Закончена глава | `--preset chapter --checkpoint chapter-2` | `MET`, `LOG-A`, `LOG-B`, `SRC`, `LNG`, `STY`, `OWN-QUESTIONS`; для `project` ещё `EVD`, `TEC` |
| Закончено описание пилота | `--preset pilot` | `EVD-A`, `EVD-B`, `LOG`, `SRC` |
| Закончено введение | `--preset custom --roles MET,LNG,STY --replicas LOG=A,B --checkpoint introduction` | `MET`, `LOG-A`, `LOG-B`, `LNG`, `STY` |
| Закончено заключение | `--preset custom --roles MET,LNG,SRC --replicas LOG=A,B --checkpoint conclusion` | `MET`, `LOG-A`, `LOG-B`, `LNG`, `SRC` |
| Закончена аннотация | `--preset custom --roles MET,LNG,LOG --checkpoint annotation` | `MET`, `LNG`, `LOG` |
| Собран DOCX | `--preset docx` | `DOC-STRUCTURE`, `DOC-VISUAL`, `MET-FORMAT`, `SRC-CROSSREF` |
| Полный черновик готов | `--preset draft` | все базовые роли, `OWN` в виде `OWN-QUESTIONS`; `DOC` вправе вернуть `not_applicable`, пока DOCX не собран |
| Основной агент внёс пакет правок (BLOCKER/MAJOR или содержательные правки) | `plan --kind targeted_recheck --findings F-…`, затем `plan --kind blind_regression --preset <пресет области>` | адресная перепроверка ролей замечаний и слепая регрессия затронутой области |
| Пакет правок только по MINOR класса `AUTO_SAFE` | `plan --kind targeted_recheck --findings F-…` (все такие замечания точки одним run) | одна профильная перепроверка ролей замечаний, без слепой регрессии |
| Перед передачей научруку | `--preset prefinal` | все девять ролей с `full_gate` |
| Финальный DOCX | `--preset final`, затем `plan --kind blind_regression --preset final` | девять ролей с `full_gate` плюс B-реплики `MET`, `LOG`, `SRC`, `EVD`, `TEC`, `DOC`; слепая волна — девять ролей новыми аудиторами |

`--roles` добавляет роли к пресету, `--replicas ROLE=A,B` задаёт реплики роли,
`--scope` описывает проверяемую область для заданий.

**`STY` в каждом втором подразделе (`strict`)** считает сам `plan`, `--roles STY`
добавлять не нужно. Номер главы берётся из `--checkpoint subsection-<глава>.<номер>`;
`STY` получает второй, четвёртый … подраздел главы: `plan` считает разные
checkpoint `subsection-<та же глава>.*` завершённых (`complete` или `reported`)
primary-run любого пресета — подраздел с продуктом или пилотом, проверенный
`--preset product`/`pilot` с таким checkpoint, тоже засчитывается. Прерванные
(`abandoned`) и незакрытые run не считаются, повторная проверка того же подраздела
чётность не сдвигает. Без номера главы в checkpoint `plan` считает завершённые run
пресета `subsection` всех глав и предупреждает об этом в `warnings`.

В `balanced` пропускается регулярная проверка подраздела (без события высокого
риска), а финальная primary-волна состоит из девяти ролей без B-реплик. В
`maximum` каждый подраздел получает `STY`, пакет источников — `SRC-CIT-A/B`,
глава — `MET-A/B`, `SRC-A/B` и по содержанию `EVD-A/B`, `TEC-A/B`, обе
финальные волны — по две реплики каждой из девяти ролей.

При ограничении числа параллельных агентов выполняй задачи одного run волнами.
Основной агент не начинает исправления, пока все задачи run не записаны.

## Сколько это стоит

Одна задача — один запуск субагента. Ориентиры для проектной ВКР:

| Точка | `balanced` | `strict` | `maximum` |
|---|---|---|---|
| Подраздел | 0 (3 при событии высокого риска) | 3–4 | 4 |
| Глава | 9 (обычная ВКР — 7) | 9 (7) | 13 (9) |
| Пакет источников | 3 | 3 | 4 |
| DOCX | 4 | 4 | 4 |
| Перед научруком | 9 | 9 | 9 |
| Финал: primary + blind | 9 + 9 = 18 | 15 + 9 = 24 | 18 + 18 = 36 |
| Пакет правок | 1 задача на роль замечаний + слепая регрессия области | то же | то же |

За всю проектную ВКР (3 главы, около 10 подразделов, 60 источников, 2 сборки
DOCX, 3 пакета правок) это примерно 120–170 задач в `balanced`, 170–230 в
`strict` и 230–320 в `maximum`, даже если ошибок не найдено. Doctor на финале
машинно требует только финальные волны и закрытые замечания; минимальный путь
к `READY_TO_SUBMIT` — 18 задач `balanced` плюс перепроверки. Промежуточные
точки дешевле ловят ошибки рано; пропуск их — осознанное решение пользователя,
его фиксируют в state.

## Реестр высокого риска

Две реплики соответствующей роли обязательны для прямой цитаты и страницы,
источника, на котором держится цель, метод или главный вывод, центрального
числа, формулы, таблицы или результата, участников и результатов пилота,
заявленной функции продукта, архитектуры или кода и отклонения от обязательной
нормы. Если реплики расходятся, назначь третью задачу с другой моделью
(`--independence diverse_models`) и сравни доказательства уровня E3/E4; спор
не решается голосованием. Одной модели нельзя давать более двух идентичных
заданий на неизменном снимке.

## Объединение одновременных событий

Если одно сохранение породило несколько событий, выбери самый широкий пресет в
порядке `final` → `prefinal` → `draft` → `docx` → `chapter` → `pilot`/`product` →
`subsection` → `sources` и добавь узкие high-risk реплики через `--roles` и
`--replicas`. Поглощённые точки перечисли в `--scope`. Задачи `primary`,
`targeted_recheck` и `blind_regression` не поглощают друг друга.

`draft` (все базовые роли и `OWN-QUESTIONS`) шире `docx`: если полный черновик
готов одновременно со сборкой DOCX, запускается `--preset draft`, и `DOC` проверяет
собранный файл (`not_applicable` для него уже недопустим). Поглощая точку главы
(последняя глава завершила черновик), добавь реплики пресета `chapter`, которых нет
в `draft`: `--replicas LOG=A,B`, в `maximum` ещё `MET=A,B` и `SRC=A,B` (для
проектной ВКР — и `EVD=A,B`, `TEC=A,B`).

## Снимок

```bash
$A validate      # только когда есть final/vkr.docx
$A snapshot
```

`snapshot` сам вычисляет входы и пишет `audit/snapshots/<sha>.json`,
`audit/snapshot-inputs.json` и отметку в `audit/manifest.json`. `plan` делает
то же автоматически, если файлы изменились. В снимок входят:

- `vkr-project.json`;
- `state/project-state` — проекция `vkr-state.md` без служебных разделов `##` с
  точными названиями «Независимый аудит», «История сессий», «Журнал текущей
  работы», «Handoff и продолжение», «Память и продолжение» (без учёта регистра и
  пробелов) и без строк «Последнее обновление…», с LF-переводами строк. Любой
  другой раздел, даже «Целевая аудитория продукта», — содержательный;
- `plan.md`, `sources.json`, `memory/claims-register.json`, `evidence/index.json`
  и каждый локальный файл, перечисленный в нём;
- `drafts/*.md`, `sources/materials/*`;
- `final/*.docx` (lock-файл Word `~$*.docx` меньше 1 КБ не учитывается),
  `audit/automated-validation.json` и `exports/build-manifest.json` — манифест
  последней сборки `build_vkr.py`.

`snapshot_manifest_sha256` — SHA-256 канонического JSON из `protocol_version`,
`validation_profile`, отсортированного по `(logical_id, kind, sha256)` массива
`inputs[{logical_id, kind, sha256}]` и `tool_versions`; строки нормализуются
NFC, хеши — в нижнем регистре, сериализация UTF-8 с `ensure_ascii=false`,
`sort_keys=true` и разделителями `(',', ':')`. Хеши задач, отчётов и замечаний
в расчёт не входят, поэтому записи аудита не меняют снимок. Хеш входа с
расширением `.json` считается по канонической сериализации: отступы, BOM и
порядок ключей объекта снимок не меняют, порядок элементов массива и значения —
меняют (нечитаемый JSON хешируется побайтно). Изменение любого входа даёт новый
снимок, и прежние волны к нему не относятся.

Doctor не читает пути из `snapshot-inputs.json`: он пересчитывает входы сам и
сравнивает результат. Поля вроде `locator` или «замороженные копии» не влияют
на проверку.

## Цикл одной проверки

```bash
$A plan --kind primary --preset chapter --checkpoint chapter-2 --json
$A brief --run <RUN_ID> --json
# каждому аудитору — свой файл audit/briefs/<RUN_ID>/<TASK_ID>.md в чистом контексте
$A record --run <RUN_ID> --task <TASK_ID> --auditor-id <ID> --report <файл с JSON-ответом> --json
$A close --run <RUN_ID> --json
$A findings --open --json
```

- `brief` пишет задание: роль и область, линзу, порядок проверки, SHA снимка и
  DOCX, список файлов для чтения, правила read-only, запрет читать чужие отчёты
  и точную схему ответа. Аудитор возвращает только JSON-отчёт.
- Основной агент сохраняет ответ в файл вне `audit/` и вызывает `record`.
  `record` проверяет схему и независимость, пишет канонический отчёт
  `audit/reports/<RUN_ID>/<TASK_ID>.json`, добавляет попытку и регистрирует
  замечания `F-<GATE>-<nnn>` в `audit/findings.json`.
- `record` отказывает, если файлы изменились после `plan` (`SNAPSHOT_STALE`):
  не правь проект, пока идёт проверка.
- `auditor_id` — латиница, цифры и `. _ -` (до 64 символов); лексемы `main`,
  `author`, `student`, `self`, `user`, `coordinator`, `claude`, `assistant`
  допустимы только в run с `--independence degraded_independence`.
- Одна задача — один отчёт. Повторная попытка той же задачи возможна только с
  `--retry-reason "…"`; причина записывается в отчёт. Отрицательный вердикт
  (`fail`, `partial`) на снимке не отменяется: последующий `pass` или
  `invalid_finding` на том же снимке оставляет замечание открытым.
- Отчёт создаётся только новым файлом: `record` никогда не перезаписывает
  существующий отчёт и не использует номер удалённого run (`REPORT_EXISTS`).
- `close` даёт `complete`, если все задачи `pass` или обоснованный
  `not_applicable`, открытых BLOCKER/MAJOR этого run нет и нет незакрытых
  `fail`; иначе `reported`. Run без единого отчёта закрывается как
  `invalidated` и не учитывается.
- Если часть отчётов не записана, `close` отказывает (`RUN_TASKS_PENDING`).
  Чтобы прекратить такой run, выполни `$A close --run <RUN_ID> --abandon --reason "…"`:
  run получает `abandoned`, незаписанные задачи — `cancelled`, замечания уже
  записанных отчётов остаются в реестре.
- Повторный `close` для `reported` пересчитывает причины по актуальному реестру:
  после исправления, `accept-risk`, `waive` или `invalid_finding` закрытый run
  больше не мешает готовности.
- `not_applicable` допустим только для `EVD` и `TEC` в `vkr_type=regular` без
  материалов продукта и для `DOC`, пока DOCX не собран (не на финале). `OWN` на
  финале — никогда.

`$A next --stage draft|prefinal|final` показывает, что делать дальше: какие
run не закрыты, какие замечания открыты и какую команду выполнить.

## Замечания и их закрытие

- `open` → `resolved`: адресная перепроверка с вердиктом `pass` на **более
  новом** снимке, чем тот, где замечание найдено, если на этом снимке по нему
  нет отрицательного вердикта. `pass` на исходном снимке замечание не закрывает.
- `open` → `rejected`: вердикт `invalid_finding` с доказательством E3/E4 от
  другого аудитора; допустимо на том же снимке, если на нём нет отрицательного
  вердикта по замечанию.
- `not_recheckable` — не вердикт о содержании: замечание остаётся открытым, а
  следующая перепроверка с `pass` его закрывает.
- `fail` или `partial` после закрытия снова открывает замечание.
- `accepted_risk`: `$A accept-risk F-… --reason "…"` только для MINOR/INFO.
  Для MINOR ролей `STY`, `LNG`, `LOG` — после трёх закрытых волн этой роли на
  трёх снимках, более поздних, чем исходный, у которых изменился текст работы
  (черновики без учёта пробелов или отпечаток `final/vkr.docx`), без новых
  замечаний уровня E2+. Правка `plan.md` или лишний пробел новой волны не дают.
- `waived`: `$A waive F-… --approval evidence/approvals/<файл>` только для
  `fix_class=SUPERVISOR_APPROVAL`. Файл одобрения руководителя непустой, лежит в
  `evidence/`, записан в `evidence/index.json` → `approvals` и входит в последний
  снимок (`APPROVAL_NOT_REGISTERED`, `APPROVAL_NOT_IN_SNAPSHOT`); изменённый или
  снятый с учёта файл возвращает замечание в `open` (`AUDIT_WAIVER_INVALID`).
- BLOCKER и MAJOR нельзя закрыть `accept-risk`.

Повторная волна на том же снимке не закрывает прежний `fail`: doctor видит
замечания всех run, а `plan` отказывается повторять ту же проверку на снимке, где
она завершилась с замечаниями. Исправь, сделай новый снимок и перепроверь.

### Когда субъективные замечания не сходятся

Для `STY`, `LNG` и `LOG` критерий сходимости такой: если три закрытые волны
роли подряд не дали новых замечаний уровня E2+, повторяющиеся MINOR можно
закрыть `accept-risk` с обоснованием пользователя. Спорный MAJOR закрывается
только тремя путями: исправлением и адресной перепроверкой на новом снимке;
вердиктом `invalid_finding` с E3/E4 (например, методичка прямо допускает
формулировку); одобрением руководителя при `fix_class=SUPERVISOR_APPROVAL`.
Число итераций само по себе аудит не останавливает: если три волны не сходятся,
основной агент сообщает пользователю `USER_EVIDENCE_REQUIRED` или просит
согласование руководителя и не заявляет готовность.

## Инвалидация связанных проверок

- новый источник — перепроверка `SRC` во всех местах его использования;
- изменение числа, таблицы или результата — `EVD`, `LOG` и связанные выводы;
- изменение пилота — `EVD`, `LOG`, `MET` и связанные источники;
- изменение технического решения — `TEC`, `LOG` и `OWN`;
- изменение цели или задачи — `MET` и `LOG` для всей работы;
- изменение структуры — `MET`, `LOG` и после сборки `DOC`;
- пересборка DOCX всегда запускает `DOC`;
- чистая пунктуационная правка — `LNG`, но не полный ансамбль.

Снимок меняется автоматически; какие роли перепроверять, решает основной агент
по этому списку.

## Две формы перепроверки

После исправления BLOCKER/MAJOR или содержательного пакета правок сначала
приведи сдаваемый файл в соответствие с черновиками — пересборка → поля →
очистка → validate → snapshot:

```bash
python <SKILL_DIR>/scripts/build_vkr.py <PROJECT_DIR>
python <SKILL_DIR>/scripts/update_docx_fields.py <PROJECT_DIR>/final/vkr.docx
python <SKILL_DIR>/scripts/clean_docx_metadata.py <PROJECT_DIR>/final/vkr.docx --in-place
$A validate
$A snapshot
```

Если пользователь правил DOCX в Word, до пересборки перенеси правки в черновики
(`import_docx.py --update`). Исправленный черновик без пересборки doctor final
отклоняет: `FINAL_DOCX_OUTDATED`. Затем:

1. **Адресная перепроверка** — `plan --kind targeted_recheck --findings F-…`.
   Задание получает номера и описание замечаний; аудитор исходной задачи её не
   выполняет. В ответе — `rechecks` с вердиктом по каждому замечанию.
2. **Слепая регрессия** — `plan --kind blind_regression --preset <область>`.
   Задание не содержит прежних замечаний и diff. Её выполняют аудиторы, которые
   не участвовали в primary этого снимка, не писали замечаний и не делали
   адресных перепроверок.

Заявление основного агента «исправлено» замечание не закрывает. MINOR класса
`AUTO_SAFE` группируются до конца точки и подтверждаются одной профильной
адресной перепроверкой (`targeted_recheck` по всем таким замечаниям) **без**
слепой регрессии — это отдельная строка матрицы. Если в пакете есть BLOCKER,
MAJOR или содержательная правка (`AUTO_CONTENT`, факты, структура), нужны обе
формы: адресная перепроверка и слепая регрессия области.

## Финальный gate

Порядок финала:

1. Черновики и реестры закончены: источники `confirmed`, утверждения
   `confirmed` с доказательствами, маркеров нет.
2. Проведён Test-30 и вопросы комиссии с пользователем; ответы записаны в
   `evidence/defense/` и внесены в `evidence/index.json` → `defense`.
3. Собран единственный сдаваемый `final/vkr.docx` (`build_vkr.py` записывает
   рядом `exports/build-manifest.json`); обновление полей в Word и очистка
   метаданных сделаны **до** снимка. Промежуточные DOCX, PDF и другие документы —
   в `exports/`: в `final/` лежит только `vkr.docx`.
4. `$A validate` без ошибок, затем `$A snapshot`.
5. `$A plan --kind primary --preset final` → `brief` → `record` → `close`.
6. `$A plan --kind blind_regression --preset final` → `brief` → `record` →
   `close` новыми аудиторами.
7. Обнови раздел «Независимый аудит» state и запиши checkpoint памяти.
8. `python <SKILL_DIR>/scripts/vkr_project_doctor.py <PROJECT_DIR> --stage final --json`.

`not_applicable` для `EVD` и `TEC` (только `vkr_type=regular` без материалов
продукта, с обоснованием в отчёте) засчитывается как пройденная реплика
финальной матрицы; для `OWN` и остальных ролей на финале `not_applicable`
недопустим.

Итог аудита не пишется в `memory/claims-register.json`: он хранится в
`audit/manifest.json`, `audit/findings.json` (их пишет инструмент) и кратко в
разделе «Независимый аудит» state, который в снимок не входит. Любая другая
правка входов после шага 4 требует нового снимка и новых волн.

Doctor final требует:

- в `final/` только `final/vkr.docx` (`FINAL_DOCX_MULTIPLE`, `FINAL_EXTRA_FILES`,
  `FINAL_DOCX_NAME`), и его текст совпадает с последней сборкой из текущих
  черновиков, `sources.json`, `vkr-project.json` и рисунков (`FINAL_DOCX_OUTDATED`).
  Сверяется отпечаток сдаваемого текста: тело, таблицы, надписи, скрытый текст,
  колонтитулы, сноски, комментарии и SHA-256 рисунков; не входят оглавление и
  номера страниц в полях. Отпечаток переживает обновление полей в Word и очистку
  метаданных, но любая правка текста в Word после сборки его меняет;
- пакет `final/vkr.docx` открывается в Word: объявлены все префиксы
  пространств имён, у частей есть типы содержимого, связи ведут на существующие
  части, элементы разметки стоят на своих местах (`w:t` внутри `w:r`, `w:tc`
  внутри `w:tr` и т. д. — `FINAL_DOCX_CORRUPT`; проверка `docx_integrity.py`).
  Предел: структурная проверка знает известные причины отказа Word, но не
  заменяет открытие в Word; отметку о том, что Word документ действительно
  открыл, ставит `update_docx_fields.py` (`word_opened` в
  `exports/docx-fields.json`, её отсутствие на final — `DOCX_FIELDS_UNCONFIRMED`);
- число страниц в `exports/docx-fields.json` совпадает с числом страниц самого
  DOCX (`docProps/app.xml` → `<Pages>`, его пишет Word) — `DOCX_PAGES_MISMATCH`;
  объём в аннотации сверяется с этим числом (`ANNOTATION_PAGES_MISMATCH`, при
  оговорке «без учёта приложений» — предупреждение `ANNOTATION_PAGES_PARTIAL`,
  без единого источника числа — `ANNOTATION_PAGES_UNVERIFIED`);
- пересчитанные входы совпадают со снимком (`AUDIT_SNAPSHOT_STALE` со списком
  файлов; `exports/docx-fields.json` тоже входит в снимок). Поэтому после
  финального снимка не запускаются повторно `build_vkr.py`,
  `update_docx_fields.py` и `clean_docx_metadata.py --in-place`: они переписывают
  байты сдаваемого файла. Повторная очистка уже чистого файла ничего не пишет
  (`"status": "already_clean"`);
- повторный запуск валидатора без ошибок (`VALIDATION_ERRORS`,
  `VALIDATOR_UNAVAILABLE`) и совпадающий с ним `audit/automated-validation.json`;
- завершённую primary-волну и более позднюю завершённую blind-волну на текущем
  снимке, обе с `--preset final`: у каждого из девяти базовых gate не меньше
  пройденных реплик `full_gate`, чем в матрице (`strict` — по две у `MET`,
  `LOG`, `SRC`, `EVD`, `TEC`, `DOC` в primary; `maximum` — по две у всех в обеих
  волнах); отчёты на месте, совпадают по SHA-256 и по полям с manifest, включая
  уровень независимости; аудиторы волн не пересекаются без учёта регистра
  (`AUDIT_PRIMARY_WAVE_MISSING`, `AUDIT_BLIND_WAVE_MISSING` с причинами по
  каждому run); волны пресетов `prefinal` и `custom` не засчитываются. Doctor
  выводит применённую матрицу в `audit.final_wave_matrix` и предупреждает
  `AUDIT_INTENSITY_LOWERED`, если финальные волны проведены с `audit_intensity`
  ниже, чем более ранние run проекта;
- ни одного открытого BLOCKER/MAJOR (`AUDIT_FINDINGS_OPEN`), ни одного
  незавершённого run (`AUDIT_RUNS_INCOMPLETE`) и ни одного незакрытого `fail` на
  текущем или записанном снимке (`AUDIT_FAIL_UNCLOSED`);
- целостный журнал аудита: каждый run с `planned_seq`, непрерывный счётчик `seq`,
  нет отчётов без записи в manifest (`AUDIT_RUN_TAMPERED`, `AUDIT_SEQ_GAP`,
  `AUDIT_REPORT_ORPHAN`, `AUDIT_REPORT_MISMATCH`);
- ответы пользователя для `OWN` (`USER_EVIDENCE_REQUIRED`), подтверждённые
  источники и утверждения; утверждение только с URL-доказательствами без
  подтверждённого источника или локальной копии не принимается.

Эти проверки ловят ручную правку отдельных полей и удаление записей. Согласованную
подделку всех файлов аудита без внешнего якоря (например, копии у руководителя)
инструмент обнаружить не может: независимость аудита держится на честной работе
основного агента.

Итоговые статусы doctor: `READY_TO_SUBMIT` — final PASS и обе волны не в режиме
`degraded_independence`; `READY_FOR_SUPERVISOR_REVIEW` — prefinal PASS или
final PASS при деградированной независимости; `NOT_READY` — всё остальное.

## OWN на финале

Интерактивную часть (Test-30, репетиция вопросов) проводит основной агент с
пользователем до снимка и записывает ответы пользователя в `evidence/defense/`.
Аудиторы `OWN` в обеих финальных волнах оценивают записанные ответы, а не
изображают пользователя. Нет записей — задача `OWN` не может быть `pass`, `plan
--preset final` отказывает с `USER_EVIDENCE_REQUIRED`.

## Что означает «автоматически»

Во время активной работы основной агент сам распознаёт событие из матрицы и
запускает нужный `plan` без отдельного подтверждения пользователя. Это не
фоновый монитор: если пользователь изменил файлы вне сессии, при следующем
обращении `vkr_memory.py status` и `snapshot` покажут изменения, прежние волны к
новому снимку не относятся.

Если `audit_autorun: false`, промежуточные точки только записываются в state
как ожидающие; прямой запрос пользователя выполняется сразу. Финальный gate
отключить нельзя: без него нет `READY_TO_SUBMIT`.

## Деградированная независимость

Если платформа не умеет запускать отдельные контексты, основной агент выполняет
роли последовательно сам и планирует run с `--independence
degraded_independence`; только в этом режиме `record` принимает `auditor_id`
вроде `main`. Такой аудит полезен как редактура, но не является независимым:
doctor ограничивает итог статусом `READY_FOR_SUPERVISOR_REVIEW`. Для
`READY_TO_SUBMIT` повтори обе финальные волны в отдельных контекстах.

Записи о независимости самоописательны: инструмент проверяет согласованность
идентификаторов и отчётов, но не может удостоверить, что разные `auditor_id`
действительно были разными контекстами. Не называй деградированный аудит
независимым.
