# State-файл: память о проекте между сессиями

ИИ-система может не видеть историю прошлого чата. Для длинной работы над ВКР
контекст хранится в проекте, а не только в переписке.

## Источники истины

| Что | Где | Кто пишет |
|---|---|---|
| Профиль требований, тип ВКР, режим, `audit_intensity`, титульный лист | `vkr-project.json` | `init_vkr_project.py`, затем основной агент |
| Читаемый паспорт, решения, стилевой профиль, краткие итоги | `vkr-state.md` | основной агент |
| Checkpoint, handoff, решения, хеши файлов | `memory/`, `logs/` | `vkr_memory.py` |
| Состояние аудита: снимок, run, отчёты, замечания | `audit/manifest.json`, `audit/findings.json`, `audit/reports/` | `vkr_audit.py` |
| Итог готовности | вывод `vkr_project_doctor.py` (`readiness`) | doctor |

При расхождении каноничен машинный файл: `vkr-project.json` для настроек,
`audit/*` для аудита. Смена профиля или режима — правка `vkr-project.json` и
state в одном checkpoint.

## Что state-файл значит для снимка аудита

Проекция `vkr-state.md` входит в снимок аудита. Из неё исключаются:

- служебные разделы уровня `##` с точными названиями «Независимый аудит»,
  «Журнал текущей работы», «История сессий», «Handoff и продолжение» (и
  «Память и продолжение» из шаблонов до 6.33) — вместе со всеми подразделами;
  регистр и пробелы не важны, но название должно совпадать целиком;
- строки, начинающиеся с «Последнее обновление».

Раздел с любым другим названием входит в снимок, даже если в нём есть слово
«аудит» или «история» (например, «Целевая аудитория продукта»). Переименование
содержательного раздела в служебный тоже меняет снимок: его текст исчезает из
проекции.

Всё остальное — паспорт, тема, структура, решения, стилевой профиль — входит в
снимок. Поэтому часто меняющиеся поля (текущий этап, следующий шаг, итог
аудита, история) держи только в исключённых разделах. После финального аудита
можно обновлять исключённые разделы; правка остальных частей state делает
снимок устаревшим и требует новых волн.

## Правила работы со state-файлом

1. **В начале каждой сессии** основной агент проверяет, есть ли state в проекте.
   - Есть — читает его, handoff, roadmap, реестр утверждений и
     `audit/manifest.json`, затем запускает `vkr_memory.py status`.
   - Нет, и пользователь начинает ВКР с нуля — intake и инициализация по
     `project-initialization.md`.
   - Нет, и нужна точечная помощь (проверить оформление, поправить абзац) —
     работать без state и не настаивать на проекте.
2. **После контрольной точки и в конце значимой сессии** основной агент сам
   обновляет state и записывает checkpoint через `vkr_memory.py record`.
   Пользователь state вручную не заполняет: агент переносит в него ответы intake.
3. Если среда не даёт записывать файлы, агент возвращает обновлённые файлы одним
   комплектом и честно ставит `filesystem_setup_pending`.

**`output_style`:** [`draft` | `final` | гибрид] — в какой подаче пишутся главы.

**`target_grade`:** [`4` | `4+` | `5`]

## Как передавать в новую сессию

В начале новой сессии пользователь пишет, например:

```
Я продолжаю работу над ВКР. Изучи state, handoff, roadmap и аудит, проверь
изменения и продолжи с последнего checkpoint. Сегодня — параграф 2.3.
```

В локальной агентной системе достаточно открыть корень проекта. В системе,
которая принимает только вложения, передай файлы из списка `continuation_files`
(`project-memory.md`): `vkr-state.md`, `vkr-project.json`, `plan.md`,
`sources.json`, `evidence/index.json`, `memory/handoff.json`, `memory/handoff.md`,
`memory/roadmap.md`, `memory/claims-register.json`, `memory/artifact-index.json`,
`audit/manifest.json`, `audit/findings.json`, `audit/snapshot-inputs.json` и
текущие `drafts/*.md` — либо ZIP проекта. Если state указывает на активный
аудит, а manifest недоступен, остановись с причиной `RECOVERY_DATA_REQUIRED` и
не начинай новый run поверх потерянного состояния.

Основной агент сначала запускает `vkr_memory.py status`. Если в выводе
`"handoff_stale": true` (файлы или журнал аудита изменились после checkpoint,
записавшего handoff — например, чат оборвался после главы), `next_actions` handoff
не выполняются: агент сверяет «Журнал текущей работы» state, `audit/manifest.json`
и изменённые файлы, записывает `vkr_memory.py record --event <event.json> --all-changed`
с новыми `current_task` и `next_actions` и только потом отвечает. Ответ начинается с:
1. краткого резюме состояния («Вижу: ВКР-проект о X, тема утверждена, написаны
   1.1–1.3, руководитель просил ссылку на Гальперина — внесена? Приступаем к 2.3»);
2. уточнения о правках, если они не отмечены внесёнными;
3. только после этого — задачи сессии.

## Правила обновления

После каждой сессии основной агент обновляет «Журнал текущей работы», одну
строку «Истории сессий», «Последнее обновление» и сводку «Независимый аудит» —
эти части не входят в снимок. При крупных изменениях — «Ключевые решения»,
«Правки научрука», «Открытые вопросы», план глав; эти части входят в снимок,
их правка после финального аудита требует новых волн.

Не клади в state полный текст глав (`drafts/`), полный список источников
(`sources.json`) и длинные рассуждения.
