# Friend-sharing protocol — координация между пользователями скилла

Этот файл — **обязательное чтение**, если ты НЕ единственный пользователь скилла vkr-mpgu в своей кафедре / институте / потоке. Без следования этому протоколу — высокий риск кросс-матчинга в Антиплагиат.Вуз между работами друзей, использующих один скилл.

## Когда применять

✅ **Применять, если:**
- Двое или более студентов используют этот скилл в одном МПГУ-потоке (или одной кафедре)
- Сдача работ происходит в один сезон (зима/лето одного года)
- Есть риск что работы попадут в одну выборку Антиплагиат.Вуз

❌ **Можно не применять, если:**
- Ты единственный пользователь скилла в своей среде
- Друзья пишут ВКР в разных вузах
- Между сдачами больше года
- Тематики продуктов **категорически разные** (бот / VR / физическое устройство / методическое пособие)

## Реальный риск кросс-матчинга

Без координации, двое студентов одной кафедры с похожими проектами получат **20-30% совпадений** в Антиплагиат.Вуз — за счёт:

1. **Одинаковая негативная сигнатура** (избегание тех же 49 ИИ-клише)
2. **Одинаковый шаблон titlepage и template-mpgu.docx** (внутренний XML)
3. **Одинаковая ГОСТ-разметка** (формат разделителей)
4. **Одинаковые humanizer-техники** (burstiness, инсайты, шероховатости)
5. **Одинаковые шаблоны таблиц** (SWOT 2×2, MoSCoW)
6. **Одинаковые якорьки**, если оба не заполнили Этап 7 интервью

С координацией — снижается до 5-10%. Безопасно.

## Шаг 1: Координация тем (до начала любой работы)

**Сядьте все вместе** (физически или в созвоне) **до того, как кто-то начал писать**. 30 минут разговора. Согласуйте:

### 1.1. Категории продуктов — не должны пересекаться

Каждый берёт **разную категорию**:
- Telegram-бот / чат-бот
- Веб-приложение / SaaS
- Мобильное приложение
- VR / AR симуляция
- Обучающая игра (десктоп)
- Методическое пособие / курс
- Аппаратный/физический проект
- Аналитический инструмент / dashboard

Если двое из вас всё равно делают **боты** — расходитесь хотя бы по:
- Целевой аудитории (студенты vs школьники vs преподаватели)
- Платформе (Telegram vs WhatsApp vs Discord)
- Функциональному фокусу (информирование vs обучение vs тестирование)

### 1.2. Технологические стеки — желательно разные

- aiogram (Python) vs telebot (Python) vs telegraf (Node)
- React vs Vue vs Svelte
- Unity vs Unreal vs Godot
- Native iOS vs Native Android vs Flutter

Если стек один — окей, но в Главе I (теория) и Главе II (анализ) каждый должен использовать **разный набор источников**.

### 1.3. Базы пилотирования — разные

- Каждый проводит пилот в своей школе / институте / организации
- Если все три студента из одного института — расходитесь по разным группам / курсам / параллелям

### 1.4. Сроки сдачи — желательно разные

- Если возможно: один сдаёт в зимнюю сессию, другие — в летнюю
- Если все в одну сессию — постараться, чтобы между сдачами на кафедру было хотя бы 2-3 недели

### 1.5. Зафиксировать договорённости

Создать общий документ (Telegram-pinned, Google Doc, Notion):
```
Коллективная договорённость по ВКР с использованием скилла vkr-mpgu

| Студент | Тема | Категория | Стек | База пилота | Сдача | Ветвь Главы III |
|---------|------|-----------|------|--------------|-------|---------------|
| А       | ...  | бот       | aiogram | ИМО МПГУ | июнь  | Б             |
| Б       | ...  | VR        | Unity  | школа №X | июнь  | А             |
| В       | ...  | веб-app   | React  | колледж Y | июнь  | А             |

Договорились не использовать одинаковые:
- структуры таблиц (А берёт SWOT, Б — PESTEL, В — TOWS)
- якорьки (каждый собирает свои на Этапе 7)
- наборы конкурентов в Главе II
- источники для теоретической базы (хотя бы 70% разные)
```

## Шаг 2: Индивидуальные настройки скилла

### 2.1. Каждый — свой `user_seed`

В state-файле каждый пользователь добавляет уникальный `user_seed`:

```yaml
user_seed: "a3f2b8c1"  # 8 hex символов, уникально для каждого
```

Сгенерировать в Python:
```python
import secrets; print(secrets.token_hex(4))
```

Этот seed используется скиллом для:
- Случайного выбора 5-7 «допустимых клише», которые НЕ вырезаются (см. ниже)
- Передачи в `clean_docx_metadata.py --seed`: повторная очистка того же файла тем же seed даёт тот же результат — но только в одном окружении Python/zlib (между разными сборками Python побайтный результат может отличаться). С `--seed` обе даты `created` и `modified` — реальная дата последнего сохранения из самого документа (значение seed на даты не влияет); без `--seed` обе равны текущему времени очистки. Дату создания скрипт в прошлое не сдвигает и не выдумывает

### 2.2. Каждый — свой `target_grade`

Один из вас целится в `5` (отлично), другой в `4+`, третий в `4`. Это меняет плотность калибровки стиля:

```yaml
target_grade: "4+"  # options: 4, 4+, 5
```

Значения — те же, что в `state-file-pattern.md` → «Стилевой профиль».

См. [humanizer-techniques.md секция «Калибровка»](humanizer-techniques.md) — ниже балл = меньше инсайтов и якорьков.

### 2.3. Каждый — свой `cliche_allowlist`

В state-файле — список из 5-7 «допустимых клише», которые скилл НЕ вырезает у конкретного пользователя. Это снижает общую негативную сигнатуру:

```yaml
cliche_allowlist:
  - "стоит отметить"
  - "в современном мире"
  - "следует подчеркнуть"
```

Чтобы выбрать **разные** клише: каждый студент случайно выбирает 5-7 из списка `data/ai_cliches.json` через свой user_seed:

```python
import json, random
from pathlib import Path
random.seed("ваш_user_seed")
cliches = json.loads((Path(r"<SKILL_DIR>") / "data" / "ai_cliches.json").read_text(encoding="utf-8"))["strong"]
my_allowlist = random.sample(cliches, 6)
print(my_allowlist)
```

В Главе I (теория) этих клише может встречаться суммарно 2-4 раза — это **уменьшает** странность отсутствия популярных академических оборотов. Где `cliche_allowlist` ищется и какие формы списка читаются — `analyzers-cli.md` → «Персональный `cliche_allowlist`».

### 2.4. Каждый — свои якорьки из Этапа 7

**Каждый обязан принести ИИ-агенту на интервью свои собственные тексты.**

- Минимум 3 разных текста на пользователя
- Не делитесь своими текстами с друзьями
- Не делитесь своим `personal_style_profile` с друзьями
- На защите тоже не обсуждайте якорьки

### 2.5. Структурные различия

Каждый выбирает разные:
- Ветвь Главы III (А или Б — кому-то одному, не всем)
- Формат конкурентного анализа в Главе II (SWOT 2×2 / TOWS / PESTEL 2×3 / просто таблица 6 столбцов)
- Порядок элементов введения (стандартный vs «методология сначала»)
- Стиль выводов по главе (нумерованный список / тезисы / связный абзац)

## Шаг 3: До финального снимка — очистка метаданных

**Каждый** очищает метаданные сдаваемого файла тем же файлом — после сборки и
обновления оглавления, **до** `vkr_audit.py validate` и `snapshot` (`quickstart.md`, шаг 4):

```bash
python <SKILL_DIR>/scripts/clean_docx_metadata.py <PROJECT_DIR>/final/vkr.docx --in-place --seed <твой_user_seed>
```

Скрипт:
- обнуляет автора, последнего редактора, заголовок, тему, ключевые слова; `revision` = 1;
- ставит `created` = `modified` — время очистки (с `--seed` — дата последнего сохранения из самого документа); дата создания не сдвигается в прошлое и не выдумывается;
- чистит `docProps/app.xml` (Company, Manager, HyperlinkBase, Template, TotalTime) и удаляет `docProps/custom.xml`;
- удаляет комментарии и принимает исправления рецензирования, отключает запись исправлений;
- с `--strip-rsid` — удаляет идентификаторы сессий правки `w:rsid*`.

`--check` ничего не меняет и возвращает код 1, если метаданные для очистки найдены.
Без `--in-place` скрипт создаёт рядом второй файл, и doctor final откажет из-за
второго DOCX в `final/`. История версий облачного хранилища вне файла не очищается.
Любое изменение `final/vkr.docx` после снимка требует нового снимка и новых волн аудита.

## Шаг 4: НЕ передавать друг другу

❌ **Никогда**:
- Свой state-файл
- Свой sources.json
- Свои drafts/*.md
- Свои якорьки и personal_style_profile
- Свои выбранные клише из cliche_allowlist
- Финальный .docx

Любое из этого, попавшее к другому, обнуляет защиту.

## Финальное правило

**Главная защита — НЕ скилл, а индивидуальная конкретика твоего продукта.** Если у тебя реальный бот с реальными цифрами, конкретные даты пилота, твои собственные архитектурные решения — это **невоспроизводимо** другим студентом, даже если он использует тот же скилл.

Все технические меры выше — добавочные слои защиты. Главный слой — **разные продукты с разной фактической базой**.
