# Чек-лист перед сдачей ВКР

Пройтись по этому списку за 3-5 дней до дедлайна. За один день все проблемы не устранить.

Пункты делятся на два вида: **машинные** проверяет `vkr_project_doctor.py` (итог —
поле `readiness`), **человеческие** — пользователь и основной агент. Пометка
«ориентир скилла» означает эвристику, а не требование методички; требования
кафедры имеют приоритет (`requirements-precedence.md`).

## Содержательная часть

### Введение
- [ ] Состав введения соответствует утверждённому плану; рекомендованные методичкой элементы (актуальность, объект, предмет, цель, задачи, методы, значимость, структура) раскрыты либо согласованно исключены
- [ ] Актуальность не начинается с «в современном мире»
- [ ] Цель сформулирована одним предложением через инфинитив
- [ ] Задачи (3-5 шт.) согласуются с параграфами работы
- [ ] Методы перечислены конкретно (не «научные методы»)
- [ ] В блоке «степень разработанности» названы реальные авторы, на которых опирается работа (ориентир скилла — 8–15)

### Основная часть
- [ ] Число параграфов и их объём соответствуют утверждённому плану; ориентир скилла — 2–3 параграфа на главу без формального минимума страниц
- [ ] Если план или научрук предусматривают выводы по главам, в конце каждой главы есть блок «Выводы по главе N» (в черновике — `## Выводы по главе`)
- [ ] Для `mpgu-09-project` — ровно три главы и все 4 этапа (анализ/проектирование/пилотирование/разработка)
- [ ] Ссылки на источники расставлены по всему тексту (не только в одной главе)
- [ ] Есть собственные таблицы / схемы / графики там, где они содержательно нужны (ориентир скилла — 3–5)
- [ ] Результаты пилота и числа подтверждены файлами в `evidence/` и записями `memory/claims-register.json`

### Заключение
- [ ] **НЕТ ссылок и цитат!** (обязательное требование)
- [ ] Нет новой информации, только итоги
- [ ] Упоминается цель и её достижение
- [ ] Подведены итоги по каждой задаче введения
- [ ] Есть проверка гипотезы (если была)
- [ ] Есть перспективы дальнейшего исследования

## Формальные требования (оформление)

Большую часть пунктов этого раздела проверяет `vkr_audit.py <PROJECT_DIR> validate`
(валидатор с профилем из `vkr-project.json`); глазами проверяется то, что
валидатор не видит. Что валидатор 6.33 считает ошибкой:

- для профилей `mpgu-*` — ошибка, для `generic` — предупреждение: нарушение
  алфавитного порядка или сквозной нумерации списка литературы, нумерация глав не
  римскими цифрами, «Аннотация» или «Содержание» в оглавлении, перезапуск нумерации
  страниц;
- во всех профилях — ошибка: номер на титульном листе, пустая пронумерованная
  страница в конце, первая страница раздела без номера, заголовки не Times New Roman,
  выравнивание основного текста влево, дубль «Глава I. Глава I.», маркеры
  незавершённого текста (в том числе в колонтитулах и сносках), необновлённое
  оглавление.

Форматирование считается эффективно (стиль абзаца, базовый стиль, умолчания
документа), поэтому ручная правка шрифта в Word не скрывает ошибку стиля.

### Страница
- [ ] Шрифт Times New Roman 14 pt, чёрный
- [ ] Межстрочный интервал 1,5
- [ ] Поля: 20/10/35/20 (верх/право/**лево**/низ) — левое **35 мм**!
- [ ] Абзацный отступ 1,25 см
- [ ] Выравнивание по ширине

### Структура
- [ ] Титульный лист — не нумеруется; все поля `title_page` в `vkr-project.json` заполнены (на титуле нет `[ЗАПОЛНИТЬ: …]`) и сверены с актуальным образцом кафедры
- [ ] Аннотация на стр. 2
- [ ] Содержание на стр. 3 (без аннотации и самого содержания в списке!), **оглавление обновлено** (`update_docx_fields.py` или F9 в Word) до очистки метаданных и снимка
- [ ] Нумерация страниц — внизу по центру или справа
- [ ] Каждая глава — с новой страницы (методичка рекомендует)
- [ ] Список литературы — после заключения
- [ ] Приложения — после списка литературы
- [ ] Клятва — последний лист (живая подпись!)

### Заголовки
- [ ] Главы — римскими цифрами («Глава I. Название», «Глава II. …», «Глава III. …»)
- [ ] Параграфы — арабскими через точку (1.1., 1.2.)
- [ ] Без точки в конце заголовка
- [ ] Расстояние от заголовка до текста — 15 мм
- [ ] Стиль заголовков единообразен во всей работе

### Ссылки в тексте
- [ ] Прямые цитаты в кавычках, сверены с оригиналом
- [ ] Ссылка [N, с. XX] стоит **до точки**
- [ ] Парафраз со ссылкой [N] (без страницы) — допустимо
- [ ] Нет ссылок в заключении
- [ ] Номера ссылок ставит сборка: в черновиках только `[@id]`, ручных `[N]` нет (кроме legacy-ссылок на целые `id` после импорта)

### Фамилии
- [ ] Во всём тексте инициалы **перед** фамилией через пробел (Н.И. Иванов)
- [ ] Нигде в тексте нет фамилии без инициалов
- [ ] В списке литературы — наоборот: фамилия, запятая, инициалы (Иванов, Н.И.)

### Язык
- [ ] **Нет личных местоимений** (я, мы, нас, наш) — заменены на безличные
- [ ] Научный стиль везде (не разговорный)
- [ ] Нет русско-английских калек («давайте рассмотрим»)

### Таблицы
- [ ] Заголовок над таблицей, полужирный, по центру, без точки в конце
- [ ] «Таблица N» в правом верхнем углу над заголовком
- [ ] У всех заимствованных таблиц — ссылка на источник
- [ ] Все таблицы упомянуты в тексте («как показано в таблице 1»)

### Рисунки
- [ ] Подпись под рисунком
- [ ] «Рисунок N — Название»
- [ ] Все рисунки упомянуты в тексте
- [ ] Нет заглушек `[ Здесь вставить рисунок… ]`

### Приложения
- [ ] Каждое — с новой страницы
- [ ] «Приложение N» в правом верхнем углу
- [ ] Заголовок приложения по центру
- [ ] Все приложения упомянуты в тексте («см. Приложение 1»)

## Список литературы

- [ ] Число источников соответствует требованиям кафедры; все источники проверены и реально использованы
- [ ] Алфавитный порядок по правилу `gost-citations.md` → «Общие правила» (кириллица раньше латиницы, нормативные и электронные — вместе со всеми, если программа не требует иного) — так сортирует `build_vkr.py`
- [ ] Сквозная нумерация
- [ ] Все источники из списка есть в тексте (сборка предупреждает `SOURCE_NOT_CITED`)
- [ ] Все ссылки в тексте указывают на реально существующие номера в списке
- [ ] Оформление по ГОСТ (см. `gost-citations.md`)
- [ ] Нет курсовых/дипломных/Википедии в качестве источников
- [ ] Для электронных ресурсов — дата обращения
- [ ] Есть актуальные источники последних лет в доле, обоснованной темой (ориентир скилла — около трети за 5 лет)
- [ ] Есть иностранные источники, если тема современная

## Проверка на оригинальность (свой предварительный аудит)

Официально Антиплагиат.Вуз работу проверит один раз. Требуемый уровень — по
документам кафедры; шкала базовой методички — `methodology-mpgu.md` → «Антиплагиат».
Пользователь может и должен сделать предварительную проверку своими силами:

- [ ] Прочитал работу вслух — нет мест, звучащих как прямая цитата из учебника
- [ ] Проверил 5 случайных фрагментов по 10 слов в поиске — не находится прямых совпадений
- [ ] Нет абзацев одинаковой длины подряд (5+)
- [ ] Нет одинаковых начал абзацев (не более 1-2 «Стоит отметить» на всю работу)
- [ ] Тройные перечисления «A, B и C» встречаются не чаще, чем раз на 3-4 страницы
- [ ] Авторские обороты — 2–3 разных безличных из `personal_style_profile` (подобраны на Этапе 7 `intake-interview.md`), не скопированные из примеров других файлов
- [ ] Правила кафедры об использовании ИИ соблюдены; если кафедра требует указать использование ИИ — оно указано в требуемой форме

## Проверка источников

- [ ] `python <SKILL_DIR>/scripts/verify_sources.py --report <PROJECT_DIR>/sources.json` завершается кодом 0: все записи `confirmed` с `verification` (статусы только `pending`, `confirmed`, `suspicious`, `rejected`)
- [ ] Выходные данные корректны (автор, год, издательство, страницы)
- [ ] Все URL работают (проверить перед сдачей!)
- [ ] Даты обращения для URL — актуальные (не 2020 год, если сдаёшь в 2026)
- [ ] Для прямых цитат — проверен номер страницы

## Физическая подготовка работы

### Что распечатать

- [ ] Сама ВКР из `final/vkr.docx` (титул + аннотация + содержание + текст + список лит + приложения + клятва)
- [ ] Отдельно: **разрешение на размещение ВКР в ИС МПГУ** (подпись живая!) — форма кафедры или `assets/permission-template.docx` (2 страницы). **При коллективном проекте разрешение оформляет каждый участник.**
- [ ] Отдельно: **отзыв научного руководителя** (его вложит научрук)
- [ ] Отдельно: **справка о проверке на антиплагиат** (предоставит вуз)
- [ ] Отдельно: **рецензия** (только для магистров, вложит научрук)
- [ ] Если требует кафедра: **справка о внедрении** с реальными данными и подписью организации апробации — форма кафедры, `assets/implementation-certificate-imo-2024.docx` или `assets/implementation-certificate.docx` (2 страницы)

### Что подписать ручкой (не сканер!)

- [ ] **Клятва** — в самом конце сшитой работы (коллективная — `assets/oath-template-collective.docx`, подписи всех участников)
- [ ] **Разрешение на размещение** — отдельным документом, каждым участником

Подписи должны быть **живыми** — отсканированные и вставленные изображения не принимаются.

### Что вшить/сшить

1. Титульный лист
2. Аннотация, содержание, текст работы, список литературы, приложения
3. Последний лист — клятва (вшивается!)
4. Пустые файлы-вкладыши для:
   - Отзыва научного руководителя
   - Разрешения на размещение в ИС МПГУ
   - Справки о проверке на антиплагиат
   - Рецензии (магистры)
   - Справки о внедрении (если требуется для проекта)

### Переплёт

- Любой способ: пружина, скрепление, папка, твёрдая обложка
- **Твёрдый переплёт — по желанию**, не обязателен

### Коллективный проект — особенности

Если ВКР в формате коллективного проекта:
- Одна сшитая работа на всех (`collective: true` и `members` в `vkr-project.json` — сборка печатает всех участников на титуле)
- В клятве — подписи **всех** участников
- Разрешений на размещение — **столько, сколько участников**: каждый оформляет своё

- [ ] Основная часть — ориентир скилла 10–12 слайдов; регламент доклада и число слайдов методичка не задаёт — сверь с кафедрой

- [ ] Ответы Test-30 и репетиции вопросов записаны в `evidence/defense/` и внесены в `evidence/index.json` → `defense` **до** снимка
- [ ] Собран единственный сдаваемый `final/vkr.docx` (`build_vkr.py`); в `final/` нет других DOCX, промежуточные — в `exports/`
- [ ] Оглавление обновлено (`update_docx_fields.py` или F9 в Word) и метаданные очищены тем же файлом (`clean_docx_metadata.py --in-place`) — **до** `validate` и `snapshot`
- [ ] `vkr_audit.py <PROJECT_DIR> validate` — без ошибок
- [ ] На финальном снимке закрыта primary-волна `--preset final` и **более поздняя** слепая волна `blind_regression --preset final`; адресной перепроверки и слепой регрессии без новой primary недостаточно
- [ ] Все девять ролей обеих волн — MET, SRC, LOG, LNG, STY, EVD, TEC, DOC и OWN — закрыты независимыми аудиторами, исправления внёс только основной агент
- [ ] Нет открытых BLOCKER/MAJOR (`vkr_audit.py <PROJECT_DIR> findings --open --json`)
- [ ] Источники и утверждения `confirmed`, факты продукта и пилота подтверждаются материалами пользователя
- [ ] `python <SKILL_DIR>/scripts/vkr_project_doctor.py <PROJECT_DIR> --stage final --json` → `"readiness": "READY_TO_SUBMIT"` (при `degraded_independence` — `READY_FOR_SUPERVISOR_REVIEW`, для сдачи нужны волны в отдельных контекстах)
- [ ] После doctor final файлы проекта не менялись; если пользователь правил DOCX — `import_docx.py --update`, пересборка и новые волны
- [ ] После финального аудита не открывай `final/vkr.docx` на запись и не пересохраняй его: любое изменение байтов требует нового снимка и финальных волн; для просмотра открывай копию или режим «только для чтения».
- [ ] После финального снимка не запускай повторно `build_vkr.py`, `update_docx_fields.py` и `clean_docx_metadata.py --in-place`: они переписывают байты сдаваемого файла, а это новый снимок и новые волны.
