# Сквозной контроль качества проекта ВКР

Этот слой объединяет детерминированные проверки, долговременную память и
независимый аудит. Он снижает риск пропущенной ошибки, но не обещает абсолютную
безошибочность и не заменяет научного руководителя, кафедру и реальные данные.

Команды ниже запускает основной агент; `<SKILL_DIR>` и `<PROJECT_DIR>` —
абсолютные пути. Коротко:

```bash
DOCTOR="python <SKILL_DIR>/scripts/vkr_project_doctor.py <PROJECT_DIR>"
AUDIT="python <SKILL_DIR>/scripts/vkr_audit.py <PROJECT_DIR>"
MEMORY="python <SKILL_DIR>/scripts/vkr_memory.py <PROJECT_DIR>"
```

## Цикл одной контрольной точки

1. Сохранить законченный материал в `drafts/*.md`, реестрах и `evidence/`.
2. `$DOCTOR --stage draft --json` — структура, JSON, память. Если doctor нашёл
   структурную ошибку или повреждённый JSON, сначала восстанови входы.
3. `$AUDIT plan --kind primary --preset <точка> --json` — снимок фиксируется
   автоматически; затем `brief`.
4. Дождаться всех отчётов аудиторов, `record` по каждой задаче и `close`.
5. `$AUDIT findings --open --json`; основной агент исправляет замечания в
   черновиках и реестрах и сохраняет резервную копию изменяемых файлов.
6. Если DOCX уже собирался: пересборка → поля → очистка → validate → snapshot
   (`build_vkr.py`, `update_docx_fields.py`, `clean_docx_metadata.py --in-place`,
   `$AUDIT validate`, `$AUDIT snapshot`); иначе только `$AUDIT snapshot`. Затем
   адресная перепроверка и слепая регрессия затронутой области (`continuous-audit.md`).
7. Обновить roadmap, handoff и раздел «Независимый аудит» state; записать
   checkpoint памяти `$MEMORY record --event <event.json> --all-changed --json`.
8. Запустить doctor повторно для текущей стадии.

Запись итогов в state и память на шаге 7 снимок не меняет: разделы state с
точными названиями «Независимый аудит», «Журнал текущей работы», «История
сессий» и «Handoff и продолжение» и строка «Последнее обновление» исключены из
проекции, а результаты аудита не пишутся в `memory/claims-register.json`. Раздел
с другим названием — даже похожим, вроде «Аудит источников» — входит в снимок.

## Стадии doctor

```bash
$DOCTOR --stage draft --json
$DOCTOR --stage prefinal --json
$DOCTOR --stage final --json
```

- `draft` — рабочая структура, JSON, state, память, дубликаты источников;
  проблемы памяти и маркеры — предупреждения и справка.
- `prefinal` — готовность к передаче руководителю: обязательные разделы
  `drafts/*.md` содержательны (не меньше 300 значимых символов без заголовков,
  комментариев и маркеров); маркеры незавершённости — ошибка, кроме
  `[ПРОВЕРИТЬ…]` (предупреждение); неподтверждённые источники — предупреждение
  со списком; открытые BLOCKER/MAJOR любого run и незавершённые run на текущем
  снимке — ошибка; устаревший снимок — предупреждение.
- `final` — дополнительно ровно один `final/vkr.docx`, актуальный снимок,
  повторный запуск валидатора, две финальные волны аудита, подтверждённые
  источники и утверждения, ответы пользователя для `OWN`, отсутствие маркеров.

Doctor работает только на чтение. Вывод: `status` (`PASS`, `FAIL`, `ERROR`),
`readiness` (`READY_TO_SUBMIT`, `READY_FOR_SUPERVISOR_REVIEW`, `NOT_READY`),
`findings` с конкретными кодами и `details`, `next_actions` с готовыми
командами. Коды возврата: 0 — PASS, 1 — FAIL, 2 — ERROR (проект недоступен).
Сбой отдельной проверки превращается в находку `INTERNAL_ERROR`, остальные
проверки продолжаются. `$AUDIT next --stage <стадия>` показывает те же шаги
вместе с незакрытыми run.

## Gate готовности

| Gate | Минимальное доказательство | Автоматический контроль |
|---|---|---|
| Workspace | структура проекта и валидные JSON | doctor `draft` |
| Requirements | методичка, профиль, приоритет документов | `--preset intake` (`MET`) |
| Plan | тема → цель → задачи → главы → результаты | `--preset plan` (`MET`, `LOG-A/B`) |
| Sources | источник существует и поддерживает тезис | `--preset sources` (`SRC-BIB`, `SRC-CIT`) |
| Subsection | законченный смысл, язык, ссылки и факты | `--preset subsection` |
| Chapter | цель главы и вывод доказаны | `--preset chapter` |
| Draft | все части согласованы | doctor `prefinal` + `--preset prefinal` |
| DOCX | оформление и визуальный рендер | `validate` + `--preset docx` |
| Defense | пользователь объясняет ключевые тезисы | Test-30, ответы в `evidence/defense/` |
| Submit | один снимок, нет открытых существенных ошибок | doctor `final` + две финальные волны |

Gate нельзя закрывать по заявлению «кажется, готово»: закрытие подтверждают
записи `vkr_audit.py` и вывод doctor.

## Финальная последовательность

1. Все разделы, источники (`confirmed`), утверждения (`confirmed` с
   доказательствами) и данные титульного листа в `vkr-project.json` готовы.
2. Test-30 и вопросы комиссии проведены, ответы пользователя записаны в
   `evidence/defense/` и внесены в `evidence/index.json` → `defense`.
3. Собран единственный сдаваемый файл `final/vkr.docx` (`build_vkr.py` пишет
   `exports/build-manifest.json`); промежуточные DOCX, PDF и другие документы —
   только в `exports/`. Обновление полей в Word (`update_docx_fields.py`) и
   очистка метаданных выполняются **до** снимка, над тем же `final/vkr.docx`.
4. `$AUDIT validate` без ошибок → `$AUDIT snapshot`.
5. Финальная primary-волна и слепая волна (`continuous-audit.md`).
6. Раздел «Независимый аудит» state и checkpoint памяти.
7. `$DOCTOR --stage final --json` → `READY_TO_SUBMIT`.

Любое изменение входов снимка после шага 4 — текста, реестров, доказательств,
`final/vkr.docx` или отчёта валидатора — требует нового снимка и новых волн.
Правка черновика без пересборки DOCX даёт `FINAL_DOCX_OUTDATED`. Если после
аудита пользователь правил DOCX в Word, перенеси правки в черновики
(`import_docx.py --update`), пересобери и начни с шага 3.

## Трассировка утверждений

Для ключевого утверждения сохраняй цепочку:

```text
claim_id → место в тексте → source_ids / evidence_ids → проверка → вывод главы
```

Ключевыми считаются определения, центральные аргументы, числа, результаты
пилота, заявленные функции продукта, технические ограничения и выводы. Схема
записи — в `project-memory.md`. Изменение доказательства меняет снимок и
инвалидирует зависимые утверждения и проверки.

## Резервные точки

Перед крупной правкой главы, пересборкой DOCX и применением пакета замечаний
основной агент копирует изменяемые файлы в
`backups/checkpoints/<timestamp>-<checkpoint>/` и записывает checkpoint памяти.
Не копируй в резервную точку пароли, cookies, API-ключи и папку `backups`
целиком. Храни минимум последнюю устойчивую версию главы и последний сдаваемый
DOCX; старые копии удаляются только по решению пользователя.

## Правила остановки

- повреждены или изменены вручную manifest, снимок или отчёты
  (`AUDIT_REPORT_MISMATCH`, `AUDIT_RUN_TAMPERED`, `AUDIT_SEQ_GAP`,
  `AUDIT_REPORT_ORPHAN`, `AUDIT_SNAPSHOT_HASH_MISMATCH`) → причина
  `RECOVERY_DATA_REQUIRED`: восстанови `audit/manifest.json` из
  `audit/manifest.json.bak` (инструмент сохраняет копию перед каждой записью),
  иначе перенеси прежние записи в `audit/legacy/` и проведи волны заново;
- не хватает факта, источника, данных пилота или ответов пользователя →
  `USER_EVIDENCE_REQUIRED`;
- требуется отступление от методички → замечание класса `SUPERVISOR_APPROVAL`,
  этап roadmap `WAITING_SUPERVISOR`, закрытие только `waive` с файлом одобрения;
- doctor или аудитор нашёл BLOCKER/MAJOR → этап не закрыт;
- снимок изменился → прежние волны к нему не относятся;
- три технических сбоя одной проверки → сообщи ограничение среды, сохрани
  состояние и не выдавай ложный PASS.

`READY_TO_SUBMIT` допустим только по выводу doctor `--stage final`.
